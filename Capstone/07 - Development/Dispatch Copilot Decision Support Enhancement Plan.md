# Dispatch Copilot Decision Support Enhancement Plan

## Outcome

Extend the existing reservation conversation with actionable recovery guidance, verified change explanations, what-if simulation, queue impact explanations, return-trip matching, and meaningful assigned-trip alerts. Keep selection, review and assignment in the same thread. This is a plan only; none of these additions is implemented by this document.

## Source-based foundation

- `src/lib/dispatch/conversation.js` already projects temporal, schedule, workload, exclusions and selected-pair evidence, with deterministic fallback answers. Its instructions correctly refuse before/after claims without a verified baseline.
- The reservation `conversation/route.js` validates inputs and permissions, fetches current evidence and validates queue tokens. It explicitly warns that queue choices alone are not contention analysis.
- `dispatch-recommendation-preparation.service.js` and `dispatch-radar.service.js` provide candidate and feasibility evidence. Reuse these and the existing eligibility/ranking logic for every new result.
- `dispatch-plan.service.js` provides bounded queue planning, currently capped at 30 requests with a deadline and a greedy/single-replacement strategy. It is not a global optimization guarantee.
- `dispatch-plan-evidence.service.js` provides revision checks and signed assignment evidence. Explanation history must never extend assignment authority.
- `use-dispatch-plan.js` distinguishes a one-second local clock from a ten-second validation request and throttled recomputation. Do not add a competing polling loop.
- `start-window-notifications.service.js` already integrates with `/api/cron/sync`, notification preferences and push outbox handling. Production still needs an external authenticated scheduler; an endpoint alone is not continuous monitoring.

Recheck these callers and existing tests before each phase. Existing notes contain historical findings; current source and verified behavior determine implementation decisions.

## Shared rules

1. Deterministic services decide eligibility, timing and trade-offs. The language model interprets questions and narrates supplied facts; it never invents evidence or executes mutations.
2. Preserve current English response style and temporal evidence rules. Future bookings cannot use current GPS as future positioning. Unknown remains unknown.
3. Keep current option identities pinned while answering or refreshing. A changed/vanished pair invalidates review, without silently selecting another option.
4. Use typed server results and allowlisted UI actions, not links/action commands generated by model prose. Each target record remains permission checked.
5. Reuse existing conversation bubbles, option cards and composer. Add compact contextual actions; no separate analysis dashboard or manual Analyze step.
6. Protect request/date/pair identity against late responses. Cancel or discard superseded requests and maintain separate per-reservation context.
7. Preserve rate limits, bounded execution, limited evidence projection and evidence-only fallback. Do not log private location records in explanations.

## Phase 1 — Actionable recovery guidance

### Behavior

When zero pairs qualify, or the selected pair becomes blocked, show the most relevant recorded blocker and one useful next step. Example: a verified shift mismatch offers a link to the substitute schedule. Missing evidence offers verification guidance, not an assurance that a resource is available.

### Implementation

- Trace existing check/reason codes and pre-filter exclusions. Add stable reason codes only where currently absent; do not classify operational failures by matching display prose.
- Map supported reason codes to short explanations and permission-aware navigation: maintenance record, pairing/substitute schedule, driver availability, capacity requirement or missing route/location evidence.
- Return compact `recoveryActions` alongside conversation evidence: reason code, affected resource, required verification, and allowlisted action/record identity. Resolve URLs in application code.
- Explain multiple independent blockers when necessary. Clearing one blocker must not imply the pair passes every other check.
- Keep recovery advisory. Opening a record never changes its status; never recommend falsifying maintenance or bypassing a hard constraint.
- After the dispatcher actually updates a source record, reuse invalidation and fresh evaluation to replace the finding.

### Acceptance

Cover zero/one/multiple blocked pairs, pre-filtered vehicles, unknown evidence, absent permissions, provider outage and a repair that resolves only one of two blockers. An excluded vehicle is never selectable through a recovery action.

## Phase 2 — Verified “What changed?” explanations

### Behavior

Compare the last displayed verified evaluation with the current one. Explain changes to eligibility, reliability band, selected-pair feasibility, or recommendation rationale. Timestamp-only changes produce no chat message. On explicit inquiry, unchanged evidence yields a short “No material change” answer.

### Implementation

- Extend server evaluation output with a minimal explanation snapshot: request/date, pair IDs, relevant check states, schedule/workload facts, evidence provenance, policy version, evaluated time and revision.
- Prefer a signed, size-bounded snapshot returned to the active conversation over a new history database. Reuse established signing patterns with a distinct purpose/version; never accept a plan token as a historical snapshot or a snapshot as assignment authority.
- Verify signature, request scope and schema before comparing. Historical revision mismatch is expected and does not invalidate historical facts; it does prevent using those facts as current authorization. Expired/unavailable baseline yields current findings only.
- Compare compatible fields by stable pair identity, not Option 1/2 position. Suppress insignificant numeric jitter using existing policy bands; explain a rank change only when supported by recorded decision reasons.
- Attach structured before/after facts to the answer. Deduplicate automatic messages by semantic change fingerprint, scoped to reservation and baseline.
- Selected review is invalidated by relevant changed evidence using existing guards. Background token renewal itself does not add a message.

### Acceptance

Cover timestamp-only refresh, changed preceding-trip release, a disappeared pair, changed recommendation order, unknown-to-known evidence, tampered/cross-request snapshots, incompatible policy versions and late responses after reservation switching.

## Phase 3 — Read-only what-if simulation

### Initial scope

Support a proposed pickup date/time and passenger count. Defer route editing, multi-stop changes and arbitrary policy overrides. Example: “What if pickup is 7 PM?” Ambiguous date/time asks a concise clarification rather than guessing a date.

### Implementation

- Add a permission-checked, rate-limited reservation simulation endpoint. Validate an allowlisted scenario schema; load the real request and overlay permitted fields on an in-memory copy.
- Natural-language extraction may propose structured inputs, but schema validation and server facts decide their meaning. Echo the interpreted date/time in Philippine time and proposed passenger count in the result.
- Audit the full preparation/radar call chain for persistence and token issuance. Provide an explicitly read-only evaluation path; `persistRoute:false` alone is not proof that every dependency is side-effect free.
- Derive hypothetical trip duration/end using existing supported duration semantics. If a defensible duration is unavailable, disclose it and withhold verified downstream feasibility.
- Recompute temporal horizon, schedules, leave, maintenance, pairings, workload and routing for the scenario date. A date change cannot retain original-date workload or GPS relevance.
- Return simulated options and a comparison with the actual booking, clearly labeled “Simulation — reservation unchanged.” Do not create assignment tokens or assignable simulated option buttons.
- Keep the actual selected pair and review separate. “Assign it” after a simulation must clarify the target and require current real-booking review; it cannot accidentally submit the previously selected actual pair.
- Offer existing reservation editing navigation where authorized. After a real edit, discard stale review and run normal recommendation/selection/assignment again.

### Acceptance

Cover Manila midnight/date rollover, ambiguous time, passenger capacity failure, future-to-immediate transition, unknown duration, route-provider outage, unsupported fields, denied access and stale scenario responses. Assert no reservation/dispatch/assignment writes and no actionable assignment token are produced.

## Phase 4 — Explain downstream queue impact

### Behavior

Explain whether using a pair reduces feasible coverage for another evaluated booking. Separate conflict with an existing commitment from competition with an unassigned request.

### Implementation

- Reuse the queue planner's bounded scope, candidate evaluations, routing memo and deadline. Compare the same queue with the candidate choice pinned against the alternative choice using consistent source revisions and policy.
- Add a small structured impact result: affected authorized request IDs, preserved/lost coverage, relevant capacity/scarcity facts, fixed-booking conflicts, scope/date and coverage completeness.
- A verified queue token alone cannot prove this comparison. If data changes between runs, discard/retry within budget or report that a reliable comparison is unavailable.
- Do not claim global optimality. For partial/capped evaluation, say “Within the evaluated queue”; incomplete evidence cannot support “the only vehicle available.”
- Initially expose this on demand through “How does this affect other bookings?” Reuse existing planner coverage decisions for ranking; do not silently introduce new scoring weights.
- No new assignment is made, and unassigned proposals never become fixed resource commitments.

### Acceptance

Cover scarce large-capacity vehicles, alternative valid pairings, competing higher-priority requests, next fixed booking conflicts, a changed queue revision, capped/deadline-limited scope and unauthorized affected records.

## Phase 4B — Return-trip matching

### Behavior and initial scope

Find an existing unassigned booking that the same driver-vehicle pair could serve after completing its outbound trip, reducing unnecessary empty travel. Present the suggestion in the current conversation, for example: “After the airport drop-off, this pairing may be able to serve another pickup nearby. Review the connecting booking?” This is sequential trip matching, not passenger pooling or a change to either booking's route/time.

Start on demand with “Find a return booking” for an assigned/scheduled or active outbound trip. Keep the search bounded by an explicit time window, candidate cap and execution deadline, reusing planner limits where appropriate. Include cross-midnight candidates within the time window rather than stopping at the service-date boundary. Disclose partial coverage. A nearby pickup alone is a follow-on opportunity; describe it as a return trip only when its destination supports the stated return direction.

### Implementation

- Reuse candidate preparation, route feasibility and queue-impact evaluation. Resolve the outbound pair, scheduled destination, expected release time and their provenance from authoritative records. Future matching uses that destination/release, never today's GPS as the future origin. Active trips require qualified progress/release estimates; an elapsed scheduled end does not establish completion.
- Reject cancelled outbound trips and exclude the same reservation, already assigned follow-on requests, duplicate matches and unauthorized records. For an unassigned outbound booking, defer matching initially rather than implying an uncommitted pairing is reserved.
- Evaluate both resources across the complete sequence: outbound release, unloading/preparation allowances, transfer to the next pickup, pickup window, follow-on trip duration, and subsequent fixed commitments. Apply shared buffer policy once. Recheck capacity, category/compatibility, valid pairing, shifts/leave, maintenance and compliance for the follow-on window.
- If destination coordinates, release time, transfer routing or follow-on duration are missing, report what needs verification and withhold a confirmed feasible match. Geographic proximity may shortlist candidates but cannot prove road travel time or safe readiness.
- Return compact match evidence: both request IDs, pair identity, release/transfer estimates with provenance, usable pickup slack, next-commitment result, queue impact, evaluation time/revision and coverage. Do not expose raw private location records to the language model.
- Rank feasible matches by service reliability and protected queue coverage first, then supported empty-travel reduction, waiting burden and workload. An efficiency benefit cannot justify missed pickups, a hard conflict or harming higher-priority commitments.
- Quantify savings only against an explicit feasible baseline using the same route-estimation basis. For example, compare outbound destination → required depot plus an independently feasible vehicle origin → follow-on pickup against the proposed outbound destination → follow-on pickup, accounting for any additional required repositioning in the same comparison window. Never assume a depot return is required or that the alternative vehicle would start at the depot. If the baseline is unknown, show estimated connecting distance/time without “km saved,” fuel savings or percentages.
- Offer a contextual “Review connecting booking” action. Open that reservation's own conversation with the suggested pair as context; obtain fresh options and explicit selection/review there. Preserve the outbound conversation and do not let “Assign it” bind to an unrelated reservation.
- Commit only the follow-on booking through the existing guarded assignment flow. Revalidate the outbound dependency, the follow-on request and intervening/next commitments under current revisions before commit. Do not auto-assign, overwrite another dispatcher's assignment or silently alter the outbound trip. If the outbound schedule changes, invalidate the uncommitted suggestion; committed follow-on risks feed Phase 5 alerts.

### Acceptance

Cover a feasible airport return, a nearby pickup with an infeasible road transfer, insufficient turnaround, unknown release/duration, capacity or shift mismatch, next fixed-trip conflict, cross-midnight pickup, active-trip overrun, cancelled outbound booking, assigned follow-on booking, concurrent follow-on assignment and changed outbound revision. Verify capped search disclosure, unsupported savings suppression, future GPS exclusion and reservation-safe selection/assignment. No-match copy says no match was found within the evaluated scope, not that none exists fleet-wide.

## Phase 5 — Assigned-trip alerts and recovery proposals

### 5A: Visible workspace

- Reuse existing source invalidation and one refresh owner. Evaluate the committed pair with its own assignment excluded from overlap checks; do not reopen unassigned ranking as dispatch authorization.
- Trigger one conversation update for a meaningful new issue: maintenance/leave conflict, failed readiness, verified timing deterioration or resource unavailability. Unknown evidence is a verification issue, not proven lateness.
- Deduplicate repeated findings. Resolution updates occur once per incident transition. Stop alert generation for cancelled/completed records and preserve in-progress lifecycle restrictions.
- Offer “Check replacement options” as a read-only action. Keep the original assignment intact while alternatives are reviewed.

### 5B: App-closed monitoring

- Inspect and extend existing cron sync, notification preferences, audience policy and push outbox rather than introducing another notification system.
- Add bounded upcoming-assignment scans with policy-defined horizons, deadlines and retry/catch-up behavior. Use database-backed incident identity and transactional deduplication across overlapping workers; inspect existing storage before choosing a minimal migration.
- Configure and verify the authenticated external scheduler, execution monitoring and missed-run recovery before claiming background monitoring works.
- Notifications carry minimal details and deep-link to the same reservation conversation. Re-fetch current state when opened; notification text is not current assignment evidence.

### Replacement commit boundary

Trace the existing reassignment lifecycle before enabling a replacement confirmation. If no suitable guarded path exists, ship alerts and proposals first; mark reassignment execution unavailable. A later commit must atomically release/reserve resources, revalidate both assignments, record the reason/audit event and preserve driver acknowledgement rules. Never auto-reassign, silently cancel a trip or send driver messages through model prose.

### Acceptance

Cover repeated/overlapping scans, incident resolution and recurrence, disabled channels, unauthorized recipients, stale GPS, hidden/reopened tabs, scheduler downtime, completed/cancelled trips and notification-open after the issue resolved. For enabled reassignment, test concurrent assignment, permission failure and ambiguous network outcomes.

For each delivery, add focused tests at the shared decision boundary and affected route/UI integration; run touched-source lint and existing authorization checks. Run the relevant regression suites and production build for integrated route/UI changes. Use a fixed clock for time-bound cases. Confirm desktop/mobile conversation behavior, keyboard actions, request switching and LLM-unavailable fallback in browser; record unavailable live checks rather than claiming them passed.

If a migration is necessary, inspect existing numbering and storage, create an idempotent migration, use `npm run db:up` then `npm run db:dump`, and verify live schema/query compatibility per repository policy. Never hand-edit generated `schema.sql`.

Read installed Next.js documentation before route/component implementation. Update this plan's delivery status, AI Advisory and SYSTEM.md after each completed phase, including actual verification and unresolved dependencies.

## Completion criteria

The dispatcher can understand a blocker, see a verified reason for a changed recommendation, explore a hypothetical booking safely, inspect relevant queue trade-offs, review a feasible return-trip match and receive useful assigned-trip issue updates in the same conversation. Every real assignment or replacement still requires current evidence and explicit dispatcher confirmation. No feature represents ranking scores as probabilities or derives fatigue from trip counts.

Planning validation: repository instructions, current conversation route, queue hook, planner/evidence exports, notification producer and relevant feature/temporal notes were inspected. No application tests or live scheduler/database checks were run for this documentation-only task.
