# Audit Logging Coverage and Load Plan

**Status:** Core implementation completed 2026-10-01; staging capacity acceptance remains open. **Prepared:** 2026-10-01. **Goal:** Cover the consequential actions identified in [[Security Audit]] while keeping audit writes, storage, and admin reads bounded. A successful sensitive disclosure must leave evidence; routine background traffic must not become audit traffic.

## Implementation status — 2026-10-01

The core plan is implemented in the application. The original review and design sections below preserve the 2026-09-30/2026-10-01 assessment and target behavior; they are historical context, not a claim that the listed gaps remain open.

- A current live snapshot on 2026-10-01 found 1,328 audit rows and approximately 552 KiB for the table and indexes. The earlier 1,324-row count remains the dated starting baseline. Neither count establishes peak write rate, insert latency, or safe production capacity.
- The shared writer uses the existing `pg` pool, bounded allowlisted metadata, 1 KiB JSON values, 256-character user agents, transaction-local 1.5-second audit statement timeouts, and a 5-second pool connection timeout. Required events share the business transaction and fail that action closed. Lower-risk events are best effort, with structured non-database failure reporting and process/pool pressure admission checks that skip them instead of competing for a saturated pool. No audit queue, second pool, partitioning, or automatic retention deletion was added.
- Audit list reads are server-filtered and cursor-paged (25 by default, maximum 50), exclude payload JSON, avoid per-page exact counts, and bound date ranges. Detail reads are separate and audited; the UI no longer polls or refreshes on focus.
- Full license responses are audited before release. Deliberate masked views use dedicated endpoints; cached mobile screen opens use a bounded per-account offline queue and replay. General roster/profile responses no longer include the license value, and the roster refresh does not generate view events.
- Consequential driver, fleet, maintenance, expense/leave, AI-provider, and mobile duty/inspection write paths now emit transaction-bound or explicitly best-effort events according to their failure policy. Duplicate submissions and no-op state changes do not create extra events. Driver license values, scans, provider secrets, and media content are excluded from audit metadata.
- Driver face-photo uploads now emit a best-effort update summary after the profile references are written. It records changed field names and outcome only; image bytes, storage keys, and signed URLs are excluded. Vehicle-document creation tests pin field-name-only metadata and rollback on required audit failure.
- The migration adding the masked-view replay key was applied with the repository migration runner and `schema.sql` was refreshed. `db:check` and the live `db:contract` pass with zero contract violations.

The focused automated suites pass **165 tests across 30 files**, covering the writer, rate limiter, audit list/detail APIs, license disclosure/view paths, driver profile/media changes, fleet/document/category/provider writes, maintenance, finance/leave decisions, and mobile submissions. Changed-JavaScript ESLint passes; the route-auth audit passes **294/294** exported methods. `db:status` reports 140 applied, 0 pending, and 0 changed; `db:check` passes and the live database contract reports zero violations. The repository has no separate staging database target configured, so the 10x event-rate exercise has not been run. Production latency/storage budgets, alert thresholds, and an approved retention policy remain open. Do not describe capacity as proven until the exercise runs against a comparable connection budget.

## Starting point and design limits

- The 2026-09-30 read-only live aggregate found 1,324 `audit_logs` rows over 2026-08-01 through 2026-09-30, with 37 actions and 29 resources. This is a count baseline, not a measured peak rate, byte size, or latency baseline. Measure those before setting production thresholds.
- `writeAudit()` currently awaits a second `pg` query, catches its own errors, and accepts unbounded JSON and user-agent input. Its comment says it never blocks, but a slow pool/insert can delay the request. The shared pool has a maximum of 10 connections per application instance and no explicit connection wait timeout. Do not add another pool for auditing.
- The audit list currently fetches up to 200 rows by default (maximum 500), including full `old_values`/`new_values`, executes an exact `COUNT(*)` per request, and uses `OFFSET`. The page then filters and paginates that subset in the browser. Its fixed action filter exposes only six of the 37 observed actions.
- `audit_logs` has indexes on `created_at`, `employee_id`, and `(resource, resource_id)`, but no event ID for replay deduplication. At the present count, a queue, partitioning, automatic purge, or several speculative indexes would add complexity without demonstrated benefit.
- The operational histories remain authoritative for their domains: `reservation_events`, inspections, attendance, expenses, fuel, and maintenance records. An audit event summarizes a consequential action; it does not copy a complete domain row or replace its history.

## Event contract and volume budget

1. Define a server-owned event catalog with stable `action`/`resource` names, trigger, actor, target ID (or a bounded ID list for a directory page), sensitivity, and failure policy. Preserve existing names for historical filtering; add specific names for access/disclosure and decisions. Supply the authenticated session at each call site. Fix the existing staff driver edit calls that pass `null` and lose `employee_id` before extending them. Pass safe IP/user-agent context to trip/dispatch transition services where the request exists, or attach a server request/correlation ID when it does not.
2. Add a shared insert function that accepts an existing transaction (`tx`) and throws, plus a bounded best-effort wrapper for lower-risk access and domain-summary events. The required writer must never swallow an error. Use the existing `pg` pool and parameterized SQL. Add a bounded connection wait and database-side query/statement timeout appropriate to measured latency; a JavaScript timeout alone does not cancel a still-running query. Set audit statement timeouts transaction-locally (`SET LOCAL`), ideally with the required insert last before commit; never leave a session-level timeout on a pooled connection or lower all business query timeouts blindly. For best-effort events, use a bounded checkout and transaction-scoped timeout with guaranteed release, and benchmark the extra round trips. Report insert errors and timeouts through non-database monitoring so a database outage does not suppress the signal.
3. Allowlist event metadata. Store IDs, changed field names, old/new *safe* status values, decision/reason codes, and outcome. Do not store passwords, OTPs, tokens, provider keys, full or masked license values, scans, images, face-photo URLs, receipt contents, or free-text reasons. Cap serialized metadata (initial target: 1 KiB per JSON value) and user-agent (initial target: 256 characters); reject oversized required events before business commit and count dropped best-effort events. Check existing callers before enforcing caps so legacy events are not silently truncated.
4. Emit one event for a successful state transition or newly inserted submission, not for each SQL statement, no-op update, validation attempt, retry, or duplicate record. Reuse trusted submission IDs only to recognize the original insert; do not use a client-supplied ID to suppress later full-license disclosures. An inspection that also starts duty can have one concise event describing both outcomes. Every full-license response is audited independently.
5. Do not audit GPS fixes, heartbeat/polling, ordinary notification reads, cached profile refreshes, or all authorization failures. Record selected high-risk denials (license reveal and audit access) with rate limiting or aggregation and no sensitive request payload. Keep automatic incident/dispatch events already recorded; do not create a second row for the same transition.

### Masked mobile views and disclosure semantics

The mobile License & Compliance screen can render a masked number from memory or AsyncStorage with no network request. A server GET log cannot prove that the screen was viewed. On each deliberate screen open, the app should generate one event with an installation-local UUID, the account/driver ID active at open, and an observed time; persist it in a small local queue if offline, and upload in a bounded batch when connectivity returns. The server accepts replay only under the same authenticated identity, records its own authoritative receive time and `source=client_offline`, and treats the client time as untrusted context. A nullable `event_key uuid` on `audit_logs` with a partial unique index for non-null keys (or an equivalent scoped unique constraint) is needed to deduplicate online retries and offline replay; the current schema has no such key. Apply it only to masked client-reported opens, never to full-license responses. Initial safety caps: 100 queued events/device, 20 events and 16 KiB per upload, 10 accepted opens/minute and 60/day per actor, and a 30-day replay age; tune from Stage 0 usage. Validate UUIDs and body size, reject/aggregate excess before inserts, and surface unsent/dropped counts. Do not make cached masked data unavailable merely because an event is waiting for connectivity. Offline events are eventual and client-reported, so they cannot provide the same assurance as a server-confirmed full disclosure.

For online masked views, use an intentional license-data request that inserts the access event before returning the masked value. The staff directory should request masked numbers for only its visible driver IDs in one bounded batch per deliberate page/filter opening; log one page event with at most 25 visible driver IDs and safe filter scope so it fits the metadata cap. Its existing 30-second roster refetch must not create license events. Include staff detail and leave-review screens in the caller inventory. Move the masked number out of general-purpose roster/profile responses only after web/mobile consumers have switched, so incidental reads cannot disclose it outside the audited path. Roll out the new endpoint and clients first, then remove the old response field after compatibility checks. An authorized full value returned from the current `include_license=1` endpoints must be logged on the server during the transition. Each prepared full response gets a distinct event; optional client intent flags and event IDs cannot suppress it. A prepared-response event may exist even when transport delivery fails, so its name must not assert client rendering.

## Audit viewer and database requirements

1. Replace browser-only filtering with validated server filters and a stable cursor on `(created_at, log_id)`. Use a small page size (initial target: 25–50), fetch `limit + 1` for `hasMore`, and remove exact `COUNT(*)` from each page. If the UI needs totals, request a separately cached/periodic summary. Return only list columns; make details a separate permission-checked request, redacted where existing payloads contain sensitive content.
2. Populate action/resource choices from the actual event catalog plus legacy values, rather than six hardcoded actions. Keep date range and actor/resource filters bounded. Log detail and export access at the API, not only in the UI.
3. Measure `pg_total_relation_size('audit_logs')`, average/p95 insert time, pool wait/active connections, daily event count by action, failed/dropped writes, audit-list p95 latency, and query plans before and after each phase. Keep query limits and a maximum date span for expensive admin searches. Review `EXPLAIN (ANALYZE, BUFFERS)` before adding a composite cursor or filter index; no new index is justified solely by the current 1,324 rows.
4. Agree on a retention and evidence-export policy with the system owner before pruning. Monitor projected storage and alert on a sustained growth or pool-wait increase relative to the measured baseline. At current size, do not add partitioning, a queue/outbox service, or a scheduled purge. If retention is later approved, archive first, delete in bounded date-based batches, and verify any `pg_cron` job live because `schema.sql` omits `cron.job`.
5. Review privileges and current `old_values`/`new_values` content for sensitive legacy data before exposing a detail endpoint. Do not scrub historical evidence or change retention without an explicit policy. Any new table/view or migration follows repository migration rules, `db:contract`, and `verify:anon`; `schema.sql` alone does not prove RLS/grant safety.

| 3 — consequential writes | Add P1 events in small batches: finance/leave, driver/privacy, fleet/maintenance, duty/inspection, AI provider. Fix leave state repeatability and provider-create ID first. | Each actual new action has one event in the healthy path and zero on no-op/retry, with correct actor/target and no sensitive value. | 4 — production observation | Release gradually and inspect counts, latency, connection use, table/index size, failures, and sampled redacted entries after each batch. Add selected denial summaries only after tuning. | No unexplained event surge or audit failures; rollback path rehearsed. |

**Capacity acceptance:** Establish the observed peak, then exercise at least 10 times that audit-event rate plus normal app traffic in a staging environment with a comparable connection budget. This exercise has not been run. The release gate is no pool exhaustion, no unbounded request waits, no lost required audit rows, no secret-bearing payloads, and acceptable p95 latency against the measured pre-change baseline. The exact latency/storage alert numbers are set from measured evidence, not from either row-count snapshot. Required-event failures must fail the protected action closed; best-effort failures must be visible and must not turn into a retry storm.

**Rollback:** Each phase is independently deployable. Disable new low-value event producers first if volume spikes; keep full-license and required mutation auditing enabled. Revert a problematic viewer query or consumer migration without deleting audit rows. If a required writer cannot keep up, reject the protected operation until fixed rather than silently dropping its event. Additive migrations remain in place and are reviewed through `npm run db:status`, `npm run db:up`, `npm run db:dump`, live catalog checks, `npm run db:contract`, and `npm run verify:anon` as applicable.
