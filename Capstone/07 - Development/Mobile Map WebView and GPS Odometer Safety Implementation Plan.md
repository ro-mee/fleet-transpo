# Mobile Map WebView and GPS Odometer Safety

## Scope and current evidence

This plan covers two residual defects found in the pending mobile map changes. It
does not change trip APIs, the database, the TomTom route lifecycle, or the
existing rule that failed live GPS posts are never queued for replay.

1. `mobile/components/TomTomMap.js` builds a WebView HTML document containing
   one inline script. Address text, popup markup, and radar markers pass through
   different JavaScript and HTML contexts. The current escaping leaves a raw
   `</script>` possible; popup HTML is placed inside a single-quoted JavaScript
   string; and marker titles are concatenated into `innerHTML`. Booking text can
   break map initialization and may execute markup in the WebView.
2. `mobile/lib/gps-odometer.js` rejects a segment more than five minutes after
   its anchor but keeps that old anchor. Later foreground fixes keep failing the
   same gap check, freezing mileage. `mobile/lib/background-tracking.js` uses
   the shared decision and then overwrites the anchor unconditionally, so the
   two tracking modes disagree.

The earlier backslash/HTML escaping and parked-jitter fixes addressed narrower
cases. Their recorded closures remain valid for those cases; these are new open
findings. No implementation or verification is claimed by this plan.

## 1. Close the WebView data boundaries

**Files:** `mobile/components/TomTomMap.js`, `mobile/lib/map-webview-data.js`,
`mobile/lib/map-webview-escaping.test.js`, and `vitest.config.mjs`.

1. Inventory every runtime interpolation into the generated HTML document and
   every string passed through `injectJavaScript`: booking addresses, popup
   labels, radar objects, titles, key/asset strings, and route/marker values.
   Keep static template code separate from runtime data. For any value outside
   a script, apply encoding for its actual HTML text, attribute, URL, or CSS
   context; do not reuse the JavaScript serializer there.
2. Add one helper that serializes a value as a JavaScript literal for an inline
   HTML script. Start from `JSON.stringify`, escape `<` as `\u003c` so user text
   cannot terminate the HTML script element, and encode JavaScript line
   separators. Insert the result as a complete expression, without wrapping it
   in another quoted string. Handle missing values explicitly.
3. Use that helper at every inline-script data insertion, including whole popup
   HTML strings and radar arrays. Continue HTML-escaping text within popup
   markup, then serialize the finished markup for JavaScript; each context
   needs its own encoding. Validate finite, in-range coordinates and other
   numeric values before interpolation, rather than trusting numeric-looking
   props. Apply ordinary JavaScript literal serialization to dynamic strings in
   `injectJavaScript` calls as well.
4. Replace radar title concatenation into `innerHTML` with DOM construction and
   `textContent`. Keep any icon markup static. Review other `innerHTML` writes
   and document why each remaining one is static or trusted.
5. Keep the current WebView bootstrap and `MAP_READY` message timing, marker
   sources, dev-only fabricated layers, popups, and route refresh behavior.
   A bridge-based bootstrap rewrite is outside this fix.

**Proof:** Test the actual HTML document generated by `TomTomMap`, including
the browser's script-element boundary and every remaining dynamic markup sink;
pure serializer tests alone are insufficient. Cover `</script>`, quotes,
backslashes, line breaks, Unicode line separators, HTML tags/event attributes,
and ordinary addresses in each actual sink. Assert hostile marker titles appear
as literal text, unsafe URL/CSS/attribute values are refused or encoded, and
invalid coordinates cannot enter executable source. Run
the focused mobile tests and changed-file lint. Smoke-check map readiness,
route, popups, and real radar markers in an Android and iOS development build
where available. A passing parser-only test is insufficient to claim the HTML
boundary is safe.

## 2. Make GPS recovery one shared rule

**Files:** `mobile/lib/gps-odometer.js`, `mobile/lib/background-tracking.js`,
`mobile/app/(app)/(tabs)/map.js`, `mobile/lib/gps-odometer.test.js`, and
`mobile/lib/background-tracking.test.js`.

1. In `accumulateFix`, detect a fix more than five minutes after the timestamped
   anchor **before** distance/speed rejection. Add zero kilometres for the
   unobserved interval and treat that fix as a recovery candidate, not an
   immediately trusted anchor. Confirm it with the next valid, time-ordered
   fix that is spatially and temporally plausible against the candidate
   (including a nearly identical parked fix; confirmation does not require
   movement). Use the existing 400 m, five-minute, and 180 km/h ceilings for
   that check, allowing zero displacement;
   rebase at the confirming fix with zero distance added. If that next fix is
   implausible (including a return from a far-outlier candidate), replace the
   candidate and await confirmation. A subsequent plausible fix can then
   accumulate. Reject invalid coordinates or non-monotonic timestamps without
   banking distance or confirming a candidate.
2. Keep the stable anchor for ordinary parked jitter, short-interval jumps,
   and teleports. Do not trust a single outlier as the next baseline; a later
   plausible fix near the retained anchor can continue normally. Keep the
   existing 400 m, 180 km/h, speed, and leg-context gates unless a focused
   test demonstrates a separate defect.
3. In the background task, persist the anchor and recovery candidate returned
   by `accumulateFix` instead of unconditionally assigning the incoming fix.
   Use the same helper and rule for both modes. Clear candidate state on
   trip/leg changes and at the existing app-state handoff boundary, which drops
   the straddling fix in both modes. Preserve the exact-once kilometre merge and
   `queueOnFailure: false` for live GPS posts. Extend the AsyncStorage context
   compatibly so older records without a candidate still load; no database
   migration is needed.
4. Update comments and the Tracking/Mobile Architecture notes to match the
   actual recovery rule. The long unobserved interval is intentionally omitted
   from odometer totals; do not fill it with straight-line or planned-route
   estimates. That may undercount a real journey but avoids unsupported
   mileage and maintenance due-date inflation.

**Proof:** Add trace tests asserting both **total kilometres and anchor state**:
long gap followed by a confirmed candidate and later distance, far outlier
after a gap followed by a return to the real position, single short-interval
teleport then return, parked jitter, missing/invalid time, leg change, trip
change, and foreground/background replay of the same fixes. Test the background
task's persisted anchor and candidate after rejected fixes and a restart;
helper-only tests would miss the current divergence. The existing
"re-anchors after a rejected segment" test must assert the claimed state or be
renamed. Run focused tests and changed-file lint. On a development build
(Expo Go cannot exercise background tracking), drive a real or replayed route
through foreground → background → foreground and a leg change; inspect the
per-leg merge and compare with the server trail. Mark device acceptance pending
if no build/device is available.

## Order, release gate, and rollback

1. Implement and review the WebView serializer and sink changes, then its
   boundary tests and device smoke check. Treat the injection path as the first
   release blocker.
2. Implement the odometer recovery and background anchor alignment, then its
   trace tests and device handoff check. Review mileage deltas on representative
   parked, tunnel/gap, and active-driving traces before shipping.
3. Run focused mobile checks and native smoke/handoff checks, then update
   `Tracking`, `Mobile Architecture`, `Bugs`, and `SYSTEM.md` with actual results.
   Close the findings for release only when both automated and applicable
   native checks pass. If no device/build is available, record code completion
   and leave production acceptance open.

If either change regresses the map or mileage, revert that code slice and its
associated status claim. The WebView patch is local to data encoding/rendering;
the GPS patch is local to the shared accumulator and background persistence.
No schema rollback is involved.

## Implementation record — 2026-10-02

Implemented the WebView serializer, context-specific popup/CSS encoding,
coordinate/radius validation, marker-field allowlist, and text-only marker
labels. Implemented two-fix stale-gap recovery and persisted the same anchor /
candidate state in the background task. Added tests against the complete
generated TomTomMap HTML/script plus foreground recovery and background
AsyncStorage behavior.

Verification passed: 26 focused mobile tests, changed-file ESLint with zero
warnings, and Android Expo export (1,424 modules). The environment has no ADB
or connected device; Android/iOS WebView rendering and background-location
handoff remain unverified. Keep production acceptance open until those native
checks are completed.
