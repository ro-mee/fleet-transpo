# Biometric App Lock Removal Plan

**Status:** Implemented, 2026-09-27. Mobile code and current-state notes are updated; touched-file ESLint passed. Automated test suites, native builds, and physical-device upgrade checks were not run.

## Scope and pre-removal behavior

Remove the optional Face ID/fingerprint **mobile app lock** only. Keep password plus emailed OTP, the existing mobile access and rotating refresh tokens, consent, offline cache, background GPS, and sign-out behavior. Keep the separate driver face-photo and face-recognition attendance system, including `face_image_url`, `driverattendance`, its API/storage flows, and its privacy-policy wording.

The lock is off by default. After password and OTP, `mobile/app/login.js` may offer enrollment if consent is current and the device can enforce it. `mobile/lib/biometric.js` prompts through the OS, then stores a non-secret `fleetops_biometric_sentinel` in SecureStore under service `fleetops.biometric` with `requireAuthentication: true`; ungated `fleetops_biometric_meta` records the account and display metadata. No biometric template or session token is stored in either item. `AppLockProvider` loads that metadata on startup and locks before the signed-in navigator mounts. It also locks after five minutes away from the foreground and shows `AppPrivacyVeil` while backgrounded. `mobile/app/(app)/_layout.js` renders `AppLockScreen` in place of the signed-in stack when locked. Unlock reads the gated sentinel; it does not contact the backend or mint a new session. The password fallback calls sign-out, which attempts to revoke the refresh family, clears the local session, and requires password plus OTP again. Normal sign-out also clears the enrollment.

The existing access and refresh tokens live in separate SecureStore keys and are **not** gated by biometrics. `AuthProvider` restores a stored session on cold start without a fresh server check. Once the lock is removed, a signed-in driver will open directly into the authenticated app on cold start and resume, subject to the existing session checks on later requests. This restores the unattended-phone exposure described in [[Authentication]] and [[Security Audit]]. The Android `FLAG_SECURE` task-switcher cover associated with the lock also goes away unless it is deliberately retained as an independent feature.

## Implementation record

- Removed the login enrollment offer, Profile settings row and screen, root provider, signed-in gate, lock screen, and privacy veil. Deleted the app-lock and biometric helper modules and their feature-specific tests.
- Removed `expo-local-authentication` and `expo-screen-capture`, regenerated the mobile lockfile, and removed the associated Android `USE_BIOMETRIC` configuration. Set the retained `expo-secure-store` plugin's `faceIDPermission` to `false` so its default usage description is not added.
- Added `clearLegacyBiometricEnrollment()` to the existing SecureStore wrapper. It independently attempts to delete both old enrollment keys, runs non-blockingly during session restoration, and is included in `clearAll()`; auth tokens are preserved during upgrade cleanup.
- Updated [[Authentication]], [[Mobile Architecture]], [[Security Audit]], [[System Overview]], and root `SYSTEM.md`. Face-photo and attendance code and consent wording were left unchanged.

## Original implementation sequence (completed)

1. **Remove UI entry points.** Delete the biometric offer modal, state, handlers, and `useAppLock` calls from `mobile/app/login.js`, leaving its password/OTP and consent navigation intact. Remove only the **Biometric Login** row from `mobile/app/(app)/(tabs)/profile.js`; keep the other Privacy & Security rows. Delete `mobile/app/(app)/profile/security.js` and verify no route or deep link still points to `/profile/security`.
2. **Remove the runtime gate.** Unwrap `AppLockProvider` in `mobile/app/_layout.js`, remove `AppPrivacyVeil`, and leave the existing `AuthProvider`, settings/theme providers, launch flow, push setup, and foreground `syncQueue()` listener in place. In `mobile/app/(app)/_layout.js`, remove the lock-ready wait and `AppLockScreen` branch while retaining the driver-session guard, consent redirect, GPS poster, and signed-in providers. Delete `AppLockScreen.jsx`, `AppPrivacyVeil.jsx`, `app-lock-context.jsx`, `app-lock.js`, `biometric-method.js`, `biometric-errors.js`, and their three dedicated test files once imports are gone.
3. **Purge legacy local enrollment on upgraded installs.** Before deleting `biometric.js`, move its two-key deletion into a small, idempotent legacy cleanup path called during app startup and sign-out. Delete `fleetops_biometric_sentinel` with `keychainService: "fleetops.biometric"` and `fleetops_biometric_meta` from the default service; handle failures independently so one failed deletion cannot prevent the other or block auth/session cleanup. Keep the cleanup on startup for subsequent retries when secure storage is temporarily unavailable. Do not delete `fleetops_access_token`, `fleetops_refresh_token`, or `fleetops_user` as part of the upgrade. Replace the `biometric.js` import/call in `mobile/lib/auth.js` with the legacy cleanup helper, then delete `biometric.js`. Verify the exact native delete behavior on Android and iOS, including an already-enrolled device. Keep `expo-secure-store`, which still owns auth storage.
4. **Remove native configuration.** Remove `expo-local-authentication` and `expo-screen-capture` from `mobile/package.json` and regenerate `mobile/package-lock.json`. Remove the `expo-local-authentication` config plugin and explicit `android.permission.USE_BIOMETRIC` from `mobile/app.json`; set the retained `expo-secure-store` plugin's `faceIDPermission` to `false`. Confirm `expo-screen-capture` has no other caller before uninstalling it. A native rebuild/release is needed for the permission and native module changes; a JavaScript reload alone does not prove them removed from an installed binary.
5. **Align documentation after implementation.** Change the current-state sections of [[Authentication]], [[Mobile Architecture]], [[Security Audit]], and [[System Overview]] to describe the actual post-removal behavior and the unattended-phone tradeoff. Preserve historical changelog/journal entries as history, with a dated removal note. Update root `SYSTEM.md`. Do not alter the attendance consent text or driver face-photo documentation.

## Verification and remaining release checks

- Source search found no app-lock imports, route references, or native dependencies under `mobile/`; the two old SecureStore key names remain only in the cleanup helper. The face-photo and attendance code is outside the changed files.
- `app.json` parses, its Face ID usage text is disabled, and the package manifest/lockfile no longer include either removed native package. `git diff --check` reported no whitespace errors.
- Automated test suites and native builds were not run. The physical-device upgrade check on Android and iOS remains necessary before release.
- Before release, exercise an already-enrolled Android and iOS install: confirm no biometric prompt or settings row appears, old enrollment items are cleared, the existing session opens, and sign-out still clears auth tokens and offline cache. Also check a fresh install, foreground sync, active-trip GPS, and driver-session/consent guards.
- Inspect the generated native manifests in a new build to confirm `NSFaceIDUsageDescription` and `USE_BIOMETRIC` are absent. The app config and dependency lock are updated, but the new binary has not been generated here.
- No backend route, table, RLS policy, or migration change is planned. `npm run db:status` and `npm run verify:auth` are optional regression evidence, not prerequisites for this mobile-only deletion.

**Release consequence:** Existing signed-in users lose the opt-in local gate immediately on upgrade. Communicate that the app will open from its stored session until it expires, is revoked, or the user signs out. Removing the lock without a replacement is an explicit reduction in unattended-device protection.
