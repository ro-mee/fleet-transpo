# 2026-08-16

## What I worked on

- **Mobile Home tab premium redesign** — rebuilt `mobile/app/(app)/(tabs)/index.js`.
  - Same data + RBAC logic as before; visual layer upgraded using the impeccable +
    high-end-visual-design direction (user chose: richer micro-motion first, fallback
    to subtle if not liked).
  - **Hero panel**: `expo-linear-gradient` indigo→near-black panel, daily-dispatch
    eyebrow, greeting + date, live-status chip (pulsing dot only when ON TRIP), assigned
    vehicle row with the existing `Plate` domain pattern.
  - **Trip card**: dominant + elevated; tonal badge, tabular departure-time pill, dashed
    route rail, guest row with open-in-maps action, full-width pill CTA with nested icon
    circle, `StatusPill`.
  - **Stats strip**: two tiles with icons + animated `CountUpText` figures.
  - **Quick actions**: 2×2 tiles, per-action tinted icon chips, chevron affordance.
  - **Micro-motion**: staggered section entrance (RN `Animated`, `useNativeDriver`),
    press-scale on CTA/FAB, live pulse only. No ambient/scroll decoration.
- **Typography → design-system spec**: switched the whole app from Inter to Archivo
  (display) + IBM Plex Sans (interface) + IBM Plex Mono (data) in `app/_layout.js` and
  `lib/theme.js`. Packages were already installed; only now loaded.
- **New reusable primitives** in `components/ui.js`: `PulsingDot`, `CountUpText`.
- Added `expo-linear-gradient` (SDK 54 matched via `npx expo install`).
- **Fixed live map not showing a route until passenger pickup** (`components/TomTomMap.js`):
  the `htmlContent` `useMemo` deps omitted `destination`, so the pickup leg never redrew
  after a trip transitioned pending → started (the origin address text is unchanged across
  that transition, so nothing invalidated the memo). Root cause confirmed against live DB:
  every trip's `origin_location_id` / `destination_location_id` is **null**, so routing
  depends entirely on the map geocoding the address text on regeneration. Added
  `destination?.lat, destination?.lng` to the memo deps so the map reloads whenever the
  trip target changes.
- **Fixed Home card "open in maps"** (`app/(app)/(tabs)/index.js`): used nonexistent
  payload fields `destination_lat`/`destination_lng`; corrected to the real
  `destination_latitude`/`destination_longitude` (and made the button guard null-safe).
- **Web: server-side pagination pilot on the Trips list** — made large tables fast.
  Root cause: `DataTable` did client-side sort/filter/paginate and pages called
  `getTrips()` with no params, so the browser downloaded up to 500 full rows (each with
  nested JSON) and filtered in-memory. Shifted work to Postgres:
  - `src/app/api/trips/route.js`: opt-in `page`/`pageSize`/`limit` + `status`/`search`/
    `sort`/`sortDir`; returns `{ rows, total, page, pageSize, counts }`. `counts`
    (total/active/completed) computed in one aggregate for the stat cards. Sort column
    whitelisted in `SORTABLE`. Search matches trip id / plate / driver name / route name.
  - `src/components/tables/data-table.jsx`: added a backward-compatible `manualPagination`
    mode (controlled `pageIndex`/`onPageChange`/`rowCount`/`onSortChange`); client models
    skipped in that mode.
  - `src/app/(dashboard)/trips/page.js`: query key includes paging/filter/sort, uses
    `keepPreviousData`, debounced search, stat cards read `counts`, export re-fetches the
    full set.
  - Updated the two other `getTrips()` consumers (`role-dashboard.jsx`, `tracking/history`).
  - DB: migration `052_server_side_pagination_indexes.sql` adds indexes on
    `trips(vehicle_id,start_time)`, `trips(driver_id,start_time)`, `trips(trip_status)`,
    `trips(deleted_at,created_at DESC)`, `dispatchschedules(request_id)`,
    `routes(origin_location_id)`, `routes(destination_location_id)`. Applied directly
    (live DB) because `db:up` is blocked by pre-existing checksum drift on applied
    migrations — idempotent `IF NOT EXISTS` so safe.
  - Two bugs found while verifying: `whereCount` used the 1-based placeholder counter
    instead of `params.length` (caused "bind message supplies 1 parameters"), and ORDER BY
    was appended after LIMIT/OFFSET. Both fixed; live SQL verified across 4 filter combos.
  - Redis deliberately NOT used — bottleneck is oversized payload + client-side filtering,
    not expensive computation.
  - **List payload optimization:** profiling `/api/trips` (756ms) showed the shared
    `TRIPS_SELECT` (`row_to_json(v.*)` of every joined table) serialized ~70KB per page
    and took ~400ms. Added `TRIPS_LIST_SELECT` (`src/lib/api/trips-query.js`) — same
    nested shapes (`vehicles`, `drivers`, `dispatchschedules`, `routes`) but only the
    fields list pages render; used in the `/api/trips` GET list route only. Detail/active/
    driver routes keep the full `TRIPS_SELECT`. Measured lean: ~7KB and ~55-120ms warm vs
    ~70KB / ~400ms. Verified through a pg Pool: cold first request ~439ms (pool connect),
    warm ~55ms.   Remaining high timings in dev (`npm run dev`) are cold-start / compile
    overhead that hits all API routes; test on a production build for clean numbers.
  - **Reservations register → server-side pagination** (`/api/integration/transport-requests`).
    Same pattern as trips: opt-in `page`/`pageSize`/`limit` + `sort`/`sortDir`; the paginated
    branch uses a lean `TR_LIST_SELECT` (only register columns, ~8KB/12 rows vs full
    `tr.*`+`row_to_json(.*)`), returns `{ rows, total, page, pageSize, counts }`, and
    **skips** `recomputeDerivedPriority` (a write path) and the conflict scan — the
    register shouldn't pay for the queue's write + advisory work. Non-paginated callers
    (queue `with_conflicts`, role dashboard, analytics) keep the full backward-compatible
    array + recompute. Refactored `reservations/page.js` to `manualPagination` +
    `keepPreviousData` + debounced search + server-side sort; filter chips map to API
    params (open→comma statuses, review→Pending, today→`pickup_date`); stat cards read
    `counts`; export re-fetches the full set. Verified lean query ~122ms/8KB and counts
    correct (231/18/6/8). Note: "Today" filter/count now use DB time (was browser-local),
    internally consistent.
  - **Transportation Queue → per-tab server pagination.** The queue is a card
    workspace (not a table), so the register's table pattern didn't map 1:1. The
    old path fetched EVERY request (incl. ~210 Completed) + ran a priority
    write-back (`recomputeDerivedPriority`, `updated_at=NOW()` on all rows) + the
    4-query conflict scan on the whole set, every 30s poll. Added `?tab=` to the
    transport-requests GET: the server buckets requests into the six lifecycle
    tabs in SQL (mirroring `queue-grouping.js`), returns only the active tab's
    page of cards via `TR_CARD_SELECT` (the fields `ReservationCard` renders) +
    all six tab totals (`counts.tabs`) from one FILTER query, and only recomputes
    priority + scans conflicts for the fetched page (small). Rewrote
    `queue/page.js`: query keyed on `[tab, page, debouncedSearch]`, debounced
    search, background refetch (keeps cards visible, no flash), and a pagination
    footer (mirrors DataTable style). Verified live: tab counts sum to 231
    (today 1 / upcoming 7 / assigned 9 / inProgress 1 / completed 210 / cancelled
    3); completed tab now ships 25 rows/22KB vs all 210; priority ordering
    (Overdue first) + card fields intact. Register/dashboard/analytics callers
    unchanged (no `tab`/`page` → full array).
  - **Fuel audit → server pagination.** Same fetch-all + client-side filter/sort
    problem as reservations. `/api/fuel` GET already had LIMIT/OFFSET but returned
    a plain array (no total) with heavy `fr.*` + `row_to_json(v.*)`/`row_to_json(e.*)`.
    Added a paginated mode: lean `FUEL_LIST_SELECT` (only the audit columns + the
    vehicle plate/name + driver employee name), whitelisted `sort`/`sortDir`
    (`FUEL_SORTABLE`), a server-side `FUEL_COUNTS_SQL` for the stat cards
    (total/pending/approved/rejected/approved_cost), and returns `{ rows, total,
    counts }`. Non-paginated callers (driver page, export) keep the full array.
    The `status` filter now maps "Approved" → approved OR completed (matches the
    tab's existing behavior) and normalizes case. Refactored `fuel/page.js`:
    query keyed on `[page, activeTab, search, sort]`, debounced search, tab →
    `status` param, `manualPagination` DataTable, stat cards read `counts`,
    export re-fetches the full filtered set. Verified live: 47 total / 6 pending /
    41 approved / 0 rejected, approved_cost 100343.32; 10 rows = 5KB.
  - **Maintenance → server pagination.** `/api/vehicle-maintenance` GET returned
    the full `vm.*` + `row_to_json(v.*)` with no paging/total. Added a paginated
    mode: lean `MT_LIST_SELECT`, whitelisted sort (`MT_SORTABLE`), server
    `MT_COUNTS_SQL` (total/scheduled/inProgress/totalCost), returns
    `{ rows, total, counts }`; non-paginated callers keep the array. Refactored
    `maintenance/page.js`: query keyed on `[page, search, sort]`, debounced
    search, `manualPagination` DataTable, stat cards from `counts`. Verified
    live: 25 total / 1 scheduled, total_cost 67916.20, 10 rows = 5KB.
  - **Audit of remaining lists — no pagination warranted.** Swept every list page
    against the same pattern and found the rest are either bounded or a different
    UI model, so forcing server pagination adds risk for little gain:
    Incidents (route already caps `limit` at 200 and is lean; the incident map +
    stat cards need the full set), Routes (bounded route catalog, and the API
    hard-codes `status='Active'` — a pre-existing bug that makes the page's
    Inactive/"all" tabs not show non-active routes), Drivers (bounded roster and
    the GET is a complex UNION with server-side travel filtering that needs the
    whole set), Vehicles (card grid, bounded fleet), Dispatch (kanban board of
    active lanes), UVVRP (per-day restriction board), Notifications (route
    already `LIMIT 50` + server-side `is_read` filter). The high-volume
    transaction-log tables were the real wins and are all converted.
