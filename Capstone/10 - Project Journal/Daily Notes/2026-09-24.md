## What I worked on

**Canonical-location structured-address migration — Phase 0 approved, Phase 1 done.**

Phase 0 (the persistence + precedence fixes) was approved and is code-complete and verified
but **not committed**. Phase 1 — preparing the address model for operational locations

### Phase 1, in three parts

**1. An `operational` address type.** Added to `ADDRESS_TYPES` in
`src/lib/address/structured.js`. **It needed no migration.** `addresses.address_type` is
`varchar(16)` with **no CHECK constraint** — `schema.sql` shows only two constraints on that
table and neither touches it — so the allowed set lives entirely in application code, and
`ADDRESS_TYPE_VALUES` is *derived* from `ADDRESS_TYPES`. Checking the DB before writing a
migration is what turned an assumed migration into zero work; a migration "to allow the new
type" would have been a no-op that spent a version number.

The two place-shaped surfaces (canonical locations, hotel base) now pass
`forcedType="operational"` to `AddressFormDialog`. They previously recorded `other` — honest,
and silent.

**2. One type relaxes one field.** An `operational` address no longer requires
`houseBuildingNumber` (`requiredDetailFields`). A terminal curb has a road and a ZIP and no
number; requiring one leaves the operator to invent a number or leave the address unrecorded,
and the first is the fabrication this layer refuses everywhere else. Street and ZIP stay
required, and **no other type is affected** — including an absent or unknown type, which takes
the strict branch.

**3. The form had to coerce the type for its whole lifetime, not just at submit.** This is the
part I nearly missed. The dialog used to force `other` at submit while validating against the
unforced `home`. That was invisible while the two rules agreed — and `operational` is the one
type where they differ, so the old shape would have demanded a house number the server never
asks for, leaving Save disabled with nothing the operator could type. Now an `effective` value
carries the forced type through validation, the required marks, the preview and submit.

## What I learned

- **`address_type` is rendered nowhere in the app.** Not one component reads `addressType`.
  It is written by `saveAddress`, read by `getAddress`, and displayed by no one — so the
  selector is the only UI consumer of an address type at all.
- **`locations` has no provenance columns.** No `provider`, no `verified`. #1/#8/#10's
  coordinates live on the location row and have nowhere to record where they came from. They
  are operator/system-supplied: #8/#10 from the hand-authored constants in
  `src/lib/naia-locations.js`, #1 from `system_settings.hotel_location`.
- **The address rows for #1/#8/#10 will carry no coordinates at all.** Both operational
  surfaces mount the dialog with `showPinMap={false}` — "one place, one point" — so the picked
  value reaches the server with null lat/lng and `saveAddress` writes NULL for both.
  The migration therefore cannot mark them verified: there is nothing in the row to verify.
- Pasay City has **201 barangays, all named "Barangay NNN"** (`1381100001`–`1381100201`).
  There is no barangay named "NAIA" or "Villamor".

## Decisions made

- **`operational` rather than overloading `other`.** `other` is the statement that no answer
  was available; an airport terminal is a specific kind of place.
- **Relax exactly one field, on exactly one type.** The trade accepted: `type` is a claim the
  caller makes, so a client wanting to skip the house number can declare itself operational.
  Preferred over a general "optional" flag, which would be indistinguishable from a bug and
  would relax the rule for surfaces that never asked.
- **No CHECK constraint added to `address_type`.** Flagged as a real open decision, not an
  oversight — defence-in-depth, but the repo's stated position is that storable values are
  enforced in application code.
- **Migration scope stays #1, #8, #10.** Not #6, #7, #9, or retired #2–#5. They did not need
  auditing: the model generalises without new concepts.

- **The pre-fill loader stays deferred (#21).** It affects locations and hotel equally, so
  it is better fixed once for all of them than bolted onto this surface.

### Two asymmetries worth naming

**POST and PUT were asymmetric, and POST was restructured to close it later the same
day.** `PUT` saves both registry rows inside one `withTransaction` and adds the ids to the
`UPDATE` that follows, so a registry refusal costs a retry and writes nothing. `POST` could
not: its employee and driver inserts went through the **Supabase client**, which is not a
`pg` transaction handle, so the addresses were written in a second transaction after
`driver_id` existed. A failure there left the driver with both FKs NULL — today's state —
surfaced as a `warning` on the response and toasted in the create form rather than hidden.
**That partial success was decided against before shipping**, and the fix was *not*
compensation: the two inserts moved onto `tx.query` inside the single transaction, so the
employee, both address rows and the driver now commit or roll back together. Full detail
under **Later still** below.

**Error keys are namespaced here but not on the locations routes.** A driver carries *two*
addresses, so an unprefixed `errors.streetRoad` cannot say which one was refused. The
helper prefixes with the request field; the *message* an operator sees is unchanged, since
`errValidation` reports `Object.values(errors)[0]`.

### Later still — `POST /api/drivers` fails hard

**The partial success the plan flagged as a risk was closed before it shipped.** `POST`
used to write the employee and driver inserts through the **Supabase client** and the two
address rows through `withTransaction`'s `pg` handle. PostgREST is a separate HTTP service,
so no amount of care could have made those two halves share a `BEGIN`/`COMMIT`, and an
address failure left a committed driver with both address ids NULL, reported as a `warning`
on the response.

The fix was **not** compensation. Both inserts are plain `INSERT`s with a `RETURNING` and a
unique-violation check and needed nothing PostgREST provides, so they moved onto `tx.query`
and the whole create became one transaction:

- The address rows are written **before** the driver row, so their ids go straight into its
  column list and there is no follow-up `UPDATE`. Reversing that order would turn "the
  driver is never inserted without its addresses" into "the driver is inserted and then
  rolled back" — a weaker guarantee — so `route.test.js` asserts the ordering and a future
  reorder fails loudly rather than quietly.
- The `warning` field is gone, along with the hand-rolled compensation that soft-deleted the
  employee when the driver insert failed. A rollback makes both dead.
- `POST` still runs its two guard `SELECT`s on the Supabase client, **outside** the
  transaction. That is a real TOCTOU window, and it is closed by the unique constraints
  inside — which is why a `23505` is translated to the same 409 rather than assumed
  unreachable.

**`PUT` was left alone, and the difference is stated rather than blurred.** Its address
writes and its driver `UPDATE` do *not* share a transaction: the addresses commit first,
then the `UPDATE` runs as a plain `query`. An address refusal still costs only a retry and
writes nothing — but a *driver-`UPDATE`* failure after it leaves one orphaned registry row.
Harmless (the registry is append-only and nothing joins it by value) and still a 500 to the
caller, but it is not atomicity, and the test says which of the two situations it is instead
of passing an assertion that implies otherwise.

**What the two route test files cover**: 19 tests. On create — both addresses, one address,
no addresses, the Supabase client never written through, address-before-driver ordering,
address failure → 500 with no driver row and no `warning` field, second-address failure
failing the whole create, driver-insert failure rolling back the employee, `23505` → 409, a
half coordinate pair → 400 with zero writes. On edit — a rename that leaves both address
columns out of the `UPDATE` entirely, a re-pick that appends without duplicating or clearing
the other, and both fail-hard paths.

**One trap worth recording, because it bit the first version of these tests.** The value
that reaches `saveAddress` carries the *server-resolved* `psgcBarangayCode`, not the one the
client sent — `validate-structured.js` overwrites it with the barangay the code resolved to.
A mock keyed on it, with a resolver double that answers with one fixed chain for every code,
makes both picks identical and hands the residential id to the emergency column. The tests
key on the composed street instead, and both files carry a comment saying so.

**What they still do not cover**, and why the manual pass below remains the real check: the
tests double `saveAddress` and the PSGC resolver, so nothing in them proves a row reaches
Postgres, that the pin lands as a real coordinate pair, or that `/drivers/<id>` renders.
