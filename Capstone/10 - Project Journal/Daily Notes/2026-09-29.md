# 2026-09-29

## What I worked on

Agent tooling, not app code: **Jev now drives OpenCode's session compaction.**

Started from a small question — *is Jev being used when this compacts?* — and the
answer was no. The `fast-jev-compaction` skill was sitting in `.agents/skills/`,
fully installed, and completely inert: its automatic path is a **Claude Code
function-hook plugin** (`hooks/hooks.json` → `fast-jev.ts`, intercepting
`session.compact` and `turn.complete`), and OpenCode does not load Claude Code
function hooks. The library was there; nothing called it.

A detour first: asked for `jevgrep` alongside it, installed it, and then removed it
— it is macOS/Linux only (`os: ["darwin","linux"]`, `EBADPLATFORM` on this Windows
box) and it was slow. `fast-jev-compaction` alone is the thing that was wanted.

**The actual constraint, and it is the whole design.** OpenCode 1.18 exposes exactly
one compaction hook, `experimental.session.compacting`, and all it can do is append to
`output.context` or replace `output.prompt`. No transcript surgery — which is the one
thing the library is for. So the honest combination is: Jev decides what survives,
OpenCode still writes the summary, and the summary is built from the Jev-reduced
transcript rather than the raw history. The verb here is *narrow what the summarizer
can see*, not *replace the summarizer*.

Read the live transcript through `client.session.messages`, mapped SDK parts to the
library's `Message[]` (each `ToolPart` becomes one `toolUse` **and** one
`toolResult` sharing its `callID` as `tool_use_id` — the SDK keeps a call and its
result in one part where the library pairs them by id), ran `compact()`, and appended
the survivors to the prompt under a `=== JEV-REDUCED TRANSCRIPT ===` header.

**Then, on the same day, two more things asked for: connect Jev to the questions I ask
you.** The request was worth taking literally rather than as "make compaction better".

**Feature 1 — the Q&A ledger is the best goal available.** Hooked
`tool.execute.before`/`after` on the built-in `question` tool, correlated by `callID`,
and fed every question-plus-your-answer into the Jev `goal`. The reasoning that made
this obviously right rather than clever: by the time a clarifying question gets asked,
I already know the shape of the problem, so the question is a sharper statement of
intent than the opening prompt. And in this very session the fact that most needed to
survive compaction — *you want the free Muse Spark* — **exists nowhere as prose**. It
is only an answer to a question. Left in the transcript it was just another tool call
Jev was entitled to drop as stale; captured out-of-band it cannot be.

**Feature 2 — advisory only, and the constraint is the feature.** Jev is asked, before
the dialog renders, whether the question is already answered and which option the
evidence supports; the answer is written into the dialog as two appended strings. It
does not reorder, does not pick, does not answer. You clicked, and you will keep
clicking. Silence on that would have been the wrong default: a system that quietly
answers "which model should be my default" from a hunch has taken a decision from the
one person entitled to it, and a confidence score does not make that safe.

**A guessed threshold is worse than no threshold.** `already_answered >= 0.75` sounded
reasonable. The one measured case — where the state said "only free, and stop asking me
to confirm" — scored **0.64** and would have been silently skipped. No error, no
warning, the feature just quietly doing nothing most of the time. Dropped to 0.6 on
the strength of a single observation, and written down as *one* observation rather than
a tuned value, because it is.

**A `tool.execute.before` hook is a network call sitting in a UI path.** Anything
awaited there delays the dialog, so the advisory is bounded at 2.5s and abandons the
request rather than waiting it out. Verified `choice` answers carry per-option
`probabilities`, which is what makes a per-option tag possible in one call.

**A store that works because of an unexamined assumption is a store that will break.**
The Q&A ledger is a module-level `Map` keyed by session — correct for the TUI and for
`opencode run`, wrong for a long-lived server serving many sessions, and
`pendingCalls` grows forever if a `question` call never reaches its `after` hook. Fine
now, recorded so it is a decision and not a surprise.

**What I learned**

**A vendored library in the right place is not the same as a library that runs.**
The skill was installed, documented, and did nothing, and the evidence that it was
inert was not in the skill at all — it was in `hooks/hooks.json`, a file whose
existence says "this is a Claude Code plugin" to anyone who opens it. Worth
remembering as a general check: *what is the automatic path wired to, and does this
tool load that thing?* A skill directory full of correct code is not a feature.

**`output.context` is silently ignored when `output.prompt` is set.** I wrote the
transcript into `context` and set the rules as `prompt`, which is the arrangement
the docs' first example shows, and the context would have been thrown away
unremarked. The docs state it; I would not have found it by running, because the
compaction still works and just quietly has less in it than you think.

**The library's default `goal` is the last three user messages, which is the wrong
end of a long conversation.** What decides whether a tool call "still matters" is the
task the session is working on, and by the time compaction fires that task is at the
*top* of the transcript while the bottom is "ok / thanks / no". Anchoring the goal to
the first substantive prompt moved the relevant call's `keepCall` from **0.30 to
0.43**. My first attempt appended the recent prompts too, on the theory that recency
is signal — it made things *worse*, because filler dilutes a goal rather than
refining it. The measurement is what caught it; the intuition was not.

**A smoke test that reports 0 requests has probably tested the pin window, not the
code.** The first end-to-end run showed `0 requests`, `0% reduction`, and every call
`-> keep (pinned)`. The library pins the newest `preserveRecentMessages` (6) and the
synthetic transcript had 7 messages, so every call sat inside the window. Nothing was
broken. But a green-looking result that is actually vacuous is the failure mode this
vault keeps asking about, and the only thing that distinguishes it is making the
fixture big enough to be interesting.

**`npm install --no-save` prunes the other no-save package.** Installing
`typescript` and `@types/node` one at a time left whichever came second missing,
which surfaced as `Cannot find type definition file for 'node'` and briefly as
`Cannot find module .../typescript/bin/tsc` — neither of which names the real cause.
Ended up typechecking from a scratch prefix anyway, which is the part I should have
started with: `~/.config/opencode/node_modules` is OpenCode's to manage, and
`bun install` runs there at startup.

## Problems encountered

- **Two config files in one directory.** `~/.config/opencode/` holds both
  `opencode.json` and `opencode.jsonc`, and they **merge**. `model` lives in the
  `.jsonc`; `compaction` and `plugin` live in the `.json`. I edited the wrong one
  first and it looked like it did nothing. This is a trap that will cost the same
  twenty minutes twice, and the fix is to merge them into one file.
- **The first plugin draft had a real bug, caught by typecheck:** I passed
  `{apiKey}` where `compact()` expects an *asker* (it needs `.ask(state, questions)`).
  It would have thrown at runtime on the first compaction of a real session. A
  hand-written `index.d.ts` for the vendored library is what made the compiler able
  to see it at all — the vendored package ships JS with no declarations.
- The `preserveRecentMessages` fixture problem above, which I initially read as
  "Jev is dropping everything I care about" and spent a probe script disproving.
- **The `already_answered` threshold was wrong on the first try** (0.75, picked out of
  thin air; the measured case scored 0.64). Nothing announced it. Found only because
  the test asserted the annotation was *present* rather than asserting the run logged
  no errors — an "it didn't crash" check would have passed.
- **Matching captured questions to answers by string comparison** was the first
  implementation, and it was wrong in a way that would misattribute answers between
  similar questions in the same batch. Replaced with object identity: the `entries`
  pushed into the bucket *are* the same live objects the `after` hook mutates, so no
  matching is needed at all.

## Decisions made

- **Keep the library's `keepThreshold` at 0.5.** The goal override moved the
  probabilities enough to matter; lowering the threshold on top of that would have
  been tuning against my own synthetic fixture rather than against a real
  conversation. Recorded as a deliberate non-change.
- **Vendor the library into `~/.config/opencode/lib/` rather than importing it from
  the project.** A global plugin loads in every directory; importing from one
  project's `.agents/` would make it break everywhere else. The library is
  dependency-free ESM, so a file copy is sufficient.
- **Every failure path degrades to prompt-only compaction** rather than blocking —
  no key, empty transcript, Jev error, history too large for the state budget. A
  compaction plugin that can fail a session is worse than one that occasionally
  summarises naively.
- **Model moved to `opencode/muse-spark-1.3-contributor-free`** (free on Zen), and
  the hand-rolled `agentrouter` OpenAI-compatible provider block deleted. The
  remaining `agentrouter` entry in `debug config` is OpenCode's own built-in provider
  from the stored credential, not that block.
- **Feature 2 annotates and never answers.** Not reorder, not pre-select, not answer —
  the only mutations are two appended strings. Recorded as a constraint, not an
  omission: the user asked to be *given* the decision, and an auto-answering advisor
  would have removed the thing they asked for.
- **The advisory is bounded at 2.5s and abandons the request on timeout**, because
  `tool.execute.before` is in the dialog's critical path. Every advisory failure leaves
  the dialog byte-identical to what the agent wrote.
- **Logged the full Jev `goal` on every compaction.** It decides every keep/drop
  verdict, so it is the first thing to check when a drop looks wrong.
- **Did not merge the two config files.** It is the right fix and it is also a change
  to a file I was not asked to restructure; noted above as its own task.

## Next steps

- **Not verified: a real auto-compaction inside a long live session, and a real
  question dialog rendering an annotation.** Every check drove the hooks directly with
  a stubbed client. The Jev calls, the SDK mapping, the prompt assembly, the Q&A
  capture and every fallback are proven; that OpenCode's real compaction path fires the
  hook, and that the TUI renders a mutated `options[].description`, is taken from the
  documented contract, not observed. The second matters more — `description` is the
  only thing the advisory writes, so if the TUI does not render it the feature is
  silently useless. The first real question I ask you is that test.
- **Re-check `already_answered` at 0.6 against real sessions.** One synthetic
  observation set it; that is a starting point, not a calibration.
- **Merge `opencode.json` and `opencode.jsonc`.**
- **The module-level `Map` state** assumes one process per session. True for the TUI
  and `opencode run`; wrong for a long-lived server, and `pendingCalls` needs a TTL.
- Consider whether `keepThreshold` wants tuning **against a real transcript** rather
  than a synthetic one, once one exists.
