## What I learned

**A stored row is a better witness than a description of one.** The report was "my
picked address and my pin are gone", and those looked like one bug. Counting
`addresses` rows split it: four rows total, 1–3 the backfilled operational
locations, 4 the driver's residential. The emergency address was never written —
client-side loss. But the residential row **did** arrive, with its house number and
`latitude`/`longitude` NULL — so that dialog **was** submitted, and its pin was lost
*before* the submit. One symptom, two mechanisms, and only the row count told them
apart.

**The pin survives only if it is the last thing you do.** `editDetail` clears the
pin on any detail edit and `selectLevel` clears it on any level selection — the
barangay included. The rule is right (an address must never be submitted carrying a
pin from the text it used to have) and the tests protect it. What is wrong is that
it is invisible: the pin step is deliberately last on a long form, so whatever was
just edited is far above the map.

**But the invisibility had a second, worse layer, and it was a bug.** Fixing the
first layer meant asking "how would the operator ever notice?", and the answer
turned out to be "they couldn't, because the map was lying." The pin map computed
its own `hasPin` from `Number(latitude)` — and `Number(null)` is `0`, which is
finite and in bounds, so a form holding no pin at all computed `hasPin = true`. The
map therefore showed a marker at `(0, 0)`, centred on the Gulf of Guinea at zoom 16
instead of the country view, captioned "Pin at 0.00000, 0.00000", and offered a
"Clear pin" button on an empty field. `DEFAULT_CENTER`, `COUNTRY_ZOOM` and
`SyncView`'s entire reason for existing were dead code. After an edit cleared a real
pin, the map went on showing a pin — so the operator's last look at the control said
everything was fine.

**`Number(null)` is `0`.** One coercion decided whether an absence was a presence,
and every consequence followed from it. The fix is to test absence before either
numeric check can mean anything.

**A guard that refuses silently is indistinguishable from a bug.** That shape
appears twice here, and the pin map adds a third: a control that misreports its own
state is worse than one that stays quiet, because it removes even the chance of
noticing.

**The 404 was never the endpoint's — and it was never a code defect.** `PUT
/api/drivers/59/account` answers 404, the route exists, and both driver and
employee are live. `handleError` has no 404 branch at all and `requirePermission`
throws only 401/403, so the response could not have come from the handler. The
`curl` then returned Next's own **HTML** not-found page rather than a JSON body —
and the answer was in the build trees: the route is present in `.next/server/` (the
production build) and completely absent from `.next/dev/server/` (the running dev
server). The dev server had never registered a route directory that was added while
it was up. **Restart it; no source changed.**

**The cheap check was the one I ran last.** I read two 404 branches, `handleError`
and `requirePermission` to prove the handler was innocent, when a single `curl`
would have said so immediately — an HTML 404 body from a dev server is a routing
problem, never a handler problem. `apiFetch`'s fallback to `res.statusText` is what
hid the distinction: the console said "Not Found" where it could have said "not
JSON, and the body is Next's not-found page".

**A comment can be true and still be worth re-deriving.** `address-pin-map.jsx`
states that the PSGC tables carry no coordinates, so there is nothing to centre on
after picking a barangay. That reads like an excuse, so I checked it rather than
believing it — `ph_barangays` is `psgc_code, city_code, name` and nothing else, and
`psgc-normalize.mjs` maps only codes and names, so the import source has none
either. The comment was right. The same re-derivation found the second wall, which
the comment does *not* mention: the geocoder that could answer instead is 403.

**"Routing only" was an inference from two endpoints, and it was wrong.** The note
in `Migrations.md` said the TomTom key is authorized for Routing only, on the
evidence of a `200` on `/routing/1/calculateRoute` and a `403` on `/search/2/search`.
I probed six endpoints and the shape is different: `/search/2/reverseGeocode`
answers `200` while `/search/2/place` — the *same product* — answers `403`.
Authorisation is per-endpoint, not per-product. So the rule I almost applied, "if
the Search API is blocked then address lookups are blocked", would have been wrong
in one direction and right by accident in the other. What is actually true is worse
than the note said: **every forward path is closed and the reverse one is open**,
which is exactly the wrong way round for this defect.

**The 403 has been hiding a data-correctness risk, not just a missing feature.**
The `barangay` column is filled from TomTom's `municipalitySubdivision`, and
`addresses.md` already says that is "an assumption, not a measurement" — no real
payload has ever been seen. The unit tests cannot settle it, because they only
assert that a field the provider does not send stays NULL, which passes either way.
So a wrong mapping could be writing wrong barangays today and every gate would stay
green. That is a stronger reason to enable the Search API than the UX gap is.

**And then the risk turned out not to need the Search API at all — I had been
blocking a question on the wrong door.** I wrote last time that enabling the Search
API was the stronger reason to chase the key, and then the answer arrived without it:
the four payloads came from `/search/2/reverseGeocode`, which has answered `200` every
time I probed it. I had already *measured* that endpoint as open, in the same session,
and still left task #4 filed as blocked-by-the-Search-API. A forward-geocoding 403
means I cannot ask "where is this address"; it does not mean I cannot ask "what is at
this point", and the second question is the one that tests a *field mapping*. The two
got filed as one blocker and stayed that way through the entire investigation.

**The mapping failed in the way that is hardest to catch: inconsistently.** Caloocan
returned `Maypajo` — a district — while its own freeform said "Barangay 28". Quezon
City returned `Balara` and Cebu City `Guadalupe`, which *are* real barangays, and Davao
returned `Calinan`, another district. Two right, two wrong, and no downstream check can
tell them apart. A field that is uniformly wrong is a bug you find; a field that is
right 50% of the time is one you ship, because every spot-check you happen to run has
even odds of confirming it.

**So the fix was to map nothing, and the tempting alternative was to parse the
freeform.** "Barangay 28" is right there in Caloocan's text — a regex would recover it.
It is the wrong move twice over. It is the same fuzzy inference the rest of this design
refuses when it declines to reconstruct a `psgc_barangay_code` from stored text, and it
could not be applied evenly anyway: three of the four payloads never name the barangay
at all, so the parser would fill exactly one address in four. The other three would
then be indistinguishable from addresses that genuinely have no barangay — the same
inconsistency, rebuilt by hand.

**The most dangerous comment in the codebase was one that was right by accident.** The
`geocode/route.js` block said a client cannot forge coordinates because write paths
"re-resolve the place id through `resolveAddress()`". The conclusion is true. The
mechanism is not: nothing imports `resolveAddress` except its own test. I found this
while establishing blast radius for the mapping fix, and it is a worse defect than a
wrong comment usually is — it points a future reader at a function that does nothing,
which is exactly the kind of lead that costs an afternoon and ends in "this code is
dead". The real mechanism is structural and stronger than the claimed one: a write path
has no parameter for a place id and none for a `verified` flag, so there is no request
shape in which a forgery could land. The one coordinate a client *does* supply is the
pin, and it is stored as the unverified manual claim it is — which the old comment
never mentioned, and which is the actual boundary.

**My first design for the zoom fix was wrong, and reading Leaflet's source is what
said so.** I proposed enabling the wheel on focus and disabling it on blur. Two
facts killed it. Clicking the map focuses it (`Keyboard._onMouseDown`) *and* places
the pin, so the activating click would drop a pin on whatever sat under the cursor
at country zoom — inventing the exact claim this component exists to refuse. And the
`+` control is a `<button>`, so using it never focuses the map container at all: the
wheel would have stayed dead for precisely the operator already struggling. The
fix became an explicit control, which is one click instead of a silent misuse of a
click that already means something else.

**A Leaflet option of `false` does not mean the feature is unavailable.** I nearly
wrote defensive code around `map.scrollWheelZoom` on the theory that
`scrollWheelZoom={false}` might not create the handler. `Map.addInitHook('addHandler',
'scrollWheelZoom', …)` creates it unconditionally and only *enables* it when the
option is truthy, so `enable()` after the fact is sound. Verified in
`leaflet-src.js`, not recalled.

**Reading the helper is not reading the route.** The plan for the loader said
"`GET /api/locations/[id]` gains `structured_address`", and I had read that file: I
found `loadLocation` at line 43 selecting `address_id` and took it at its word. The
file has **`PUT` only** — `loadLocation` is PUT's private helper, and there was no GET
to add a field to. It was caught while writing the handler, not while reading, and the
correction was small, but the shape of the mistake is worth keeping: I read a *function
that looked like a handler* and recorded it as one. The tell was there and cheap —
`grep '^export async function'` on the file — and I did not run it until the edit
would not apply.

**The best place for a round-trip test is beside the half that already exists.** I had
planned a new `load-structured.test.js`. `address.service.test.js` already had the two
things the round trip needs and that are expensive to reinvent: a fixture row built
from the INSERT's **own column list**, and a `project()` that narrows that row to the
columns the SELECT actually names — so a column dropped from either statement fails a
test instead of being silently restored by the fixture. Putting the loader in that file
turned "the mapping is lossless" from a comment into a journey through the real
functions. Two files holding half the mapping each is exactly how the two halves stop
agreeing while both look complete — which is the same failure the file's own history
already records, four structured columns written for a release and never read.

**A task description is a document about the past, and it does not update itself.** Task #27
asked for a decision on the POST partial-success path "before this ships" — and the path had
already been removed, two commits earlier, by the change that made the create atomic. The
description was written while the question was open and never revised when it closed. Two
more of its premises were stale in the same direction: "the driver routes have no tests at
all" (POST and PUT both have them) and "neither `[id]` route has a test" (the `[id]` route had
a PUT test; only GET was uncovered). A to-do written before the work describes a state that
no longer exists by the time anyone reads it, and the cost of trusting it runs both ways —
re-deciding something already settled, or declaring a gap that is not there. Reading the code
first turned three items of work into one.

**"Five tests passed on the first run" is not evidence, and the remedy is to break the code on
purpose.** The new GET test exists to catch one specific defect — the two address loaders
swapped, so a driver's next-of-kin's address renders as their home, one Save away from being
written back as the truth. It passed immediately, which is exactly the case where a test is
most likely to be decorative: fixtures that accidentally agree, or an assertion that would
hold under any wiring, both look identical to a working test from the green side. Swapping
`driver.address_id` and `driver.emergency_contact_address_id` at `[id]/route.js:124-125`
failed exactly 2 of the 5 — the anti-swap test and the legacy-refusal test — and left the
other 3 green. Predicting that split beforehand is what makes it evidence rather than a
coincidence: it confirms both that the tests bite and that my account of *which* assertions
carry the check is right. The three that stayed green genuinely do not depend on slot order.

**A mirror test is not a copy of the test it mirrors.** The locations GET needed the same
contract pinned as the driver GET, and the tempting move was to copy the file across. Two of
the driver file's five tests describe a defect that cannot exist on a location: there is one
address on a location, so the two loaders cannot be swapped. Copying them would have produced
tests asserting nothing this route can get wrong — green forever, and read as coverage. What
was genuinely different had to be found by reading the route instead: the `isId` guard sits
*above* the query rather than falling out of it, so a junk id costs no round trip; and this is
the route whose permission the hotel page borrows. Deciding which tests to drop took longer
than writing the ones to keep — for a while the file read as a strictly weaker version of its
sibling, which is the wrong instinct: it covers fewer failure modes because this route *has*
fewer, not because it was tested less carefully.

**A checksum is not a record of what a migration did, only that it ran.** The ledger keys each
apply by filename and stores `sha256(content)`, truncated and LF-normalised — and a checksum
**cannot be inverted**. So "this migration was applied" and "this migration did X" are different
claims, and only the first is recoverable from the database. That is why `130` is labelled a
*reconstruction* rather than a restore: it re-creates the seven object-groups the live catalog
still describes, read off `schema.sql`, `pg_get_functiondef` and `cron.job`, and it cannot know
what those six files did that left no structural trace. `063`, the shipped twin of `121`, is
what makes that concrete rather than paranoid — it carried an `UPDATE` backfilling from a
description regex, and a database rebuilt from the files alone would have silently lacked that
backfill with nothing on screen to show for it.

**A list is not evidence until someone checks what is on it.** The "ledger-only migrations"
finding had been copied forward through four documents — `AGENTS.md`, `SYSTEM.md` and two daily
notes — each restating a count that nobody had re-derived. Three of the entries were not losses
at all, and one document listed `120_temp_password_invite`, which *is* on disk. The command was
right every time; reading its output as "every name here is a lost file" was the error, and it
survived by being plausible and by being repeated.

**A procedure written from the plan describes the plan, not the system.** Steps 9–11 of the
runbook were written by restating what the loader was *meant* to do, and all three were wrong the
same way: they described an intention and never the data. Step 11 said a legacy row shows why it
could not be reopened; the only reason anyone can produce is `no-address-id`, which by design says
nothing. Step 9 said the same. The pin expectation put a marker on a row whose coordinates are
NULL. Not one of those was caught by re-reading the prose — each fell out of opening the component
or counting the table, and every one would otherwise have been discovered by an operator
mid-pass, with no way to tell a wrong expectation from a real defect. **A step that predicts
behaviour is a claim, and a claim deserves the same evidence a test gets** — the difference being
that a test is falsified deliberately before anyone leans on it, and a runbook is falsified by
whoever follows it. That is the expensive direction, and it cost three corrections to one screen
in one day before the pattern was named.

**The reachable case is often the boring one, and that is the case worth checking.** The instinct
on reading four refusal reasons is to want all four exercised, and the honest answer was that
three of them cannot be produced at all: they need data no operator can create. What remains is
the case the design deliberately keeps silent — correctly — which means the step's job inverted.
It stopped being "confirm the reason appears" and became "confirm no reason appears", and the
second is the assertion a person would never have written from the plan, because from the plan the
silence looks like the bug.

**"I did submit" and "the button was greyed out" are both true, and the word "submit" is what hid
the cause.** The entry recorded this loss as *closing the dialog with Cancel, Escape or the
backdrop* — an operator choosing a discarding exit — and the operator had confirmed the pick
happened. Both statements were honest, and the mechanism was still wrong. There are two submits in
this UI: the dialog's "Use this address" and the outer form's Save. The operator submitted the
form. The dialog **could not** be submitted, because the address was incomplete and the button was
disabled, so the only exits on offer were the discarding ones. The recorded mechanism described the
exit that was taken; it was not the reason it was taken, and siting the fix at the exit rather than
at the disabled button is why the residual gap outlived the fix. The general shape: **a mechanism
can be consistent with every measurement and still be the wrong mechanism.** The stored row proved
nothing was written and could never say why, so the only instrument that could separate the two
readings was one question to the person who had been at the screen.

**Ruling the candidates out is what makes that one question decisive.** Four junctions could have
lost that pick, and three were eliminated by reading code rather than by asking — the guard, the
payload builder, the route, and, after a doubt worth chasing, the pin map's `onChange` signature.
That left exactly one thing to ask, so the answer settled it in a sentence instead of opening a
round of guesses. The cheap move is to ask first; the better one is to ask once, at the junction
where the answer changes what you do next.

**A disabled control that explains itself elsewhere is the same silent refusal, and this one costs
a write.** The pin map misreported a state; this refuses an action. Both leave the operator with
nothing to act on, and the dialog *does* render the reason — "N required fields left", one line per
field, from the same `structuredErrors` the server validates with. It sits above the footer on a
form whose pin step and preview are below it, so the button reads as broken rather than as unready.
The useful lesson is about placement rather than visibility: "it is on screen somewhere" is not the
same claim as "it is where the person is looking", and whoever wrote the layout decides which of
those is true.

**A negative result is only as good as the search that produced it, and the tools that hide
things do not say so.** I grepped the repo for `CIRCLE_NODE_TOTAL`, got "No matches found", and
told the operator the variable was cargo cult and that the runbook was asserting something false.
Both claims were wrong, and the grep was never evidence for either: ripgrep applies ignore rules
even to a path passed explicitly, so `node_modules` was skipped and "no matches" meant "no search".
The string was in the tree the whole time, at `next/dist/server/config-shared.js:202`, as the
default for `experimental.cpus` — which is exactly what `getNumberOfWorkers` reads. A second pass
made it worse rather than better: reading `build/index.js` directly and finding no env var *there*,
I concluded the lever was dead, without following the field it actually reads back to where its
default is set. Two confident misreadings of one file pair, each reported as a finding.

What corrected it was `grep -rl` over `node_modules` through bash, where ignore rules do not
apply. The near-miss had teeth: that "correction" was about to be written into the runbook as a
fix, which would have deleted this machine's only working build lever from the document whose job
is to preserve it — the same failure mode the runbook exists to catch, aimed at the runbook. The
discipline that would have prevented it is cheap: when a negative result is about to become a
recorded claim, check that the search actually covered the place the answer would live.

## Decisions made

- **Fix the close path, do not touch the anti-stale rule.** The dialog already
  preserved input after a *failed* save but discarded it on the ordinary exit; the
  prompt closes that asymmetry. The pin-clearing rule is required by the migration
  and stays.
- **Add the pin notice only after the user asked for it.** It is a real second
  defect with the same symptom, but an in-form edit rather than an exit path, so it
  was recorded in Bugs.md first rather than smuggled into the approved change.
- **Fix `hasPin` in the pin map, though it was outside the approved scope.** Every
  consequence of the `Number(null)` bug is deterministic, so the change is a strict
  improvement with no behavioural risk — and the notice would have contradicted the
  screen, telling the operator to click a map that was still showing a phantom
  marker. Reported as a finding rather than absorbed silently.
- **Leave the map's bounds and finiteness checks alone.** Only the ORDER changed —
  absence tested first, then the numeric guards, which still do their job on a
  malformed pair.
- **`isSameStructuredAddress` compares blank as absent.** `""`, `null` and a missing
  key all mean "no value here"; without that, an `initialValue` arriving short an
  optional text field would prompt on a form nobody touched. `false` and `0` are
  values and are left alone.
- **Do the wheel before deciding between the geocoder and a gazetteer.** It is the
  only part of the sync complaint that needs no key, no data and no migration, and
  it removes the ten `+` presses from country zoom to street level on its own. It
  does not fix the complaint and I have not written that it does — it makes the hunt
  shorter, not unnecessary.
- **Ask for the wheel with a control, not with focus.** Focus is a silent trigger
  that here collides with placing a pin and misses anyone using `+`. An explicit
  button keeps the original promise of `scrollWheelZoom={false}` — the page scrolls
  normally until someone says otherwise — and costs one click in a state where the
  operator is about to spend many.
- **The map centres; it never places the pin.** Whatever C or D turns out to be, a
  geocoded street centre or a barangay centroid moves the view only. The pin stays
  a thing a person clicked, stored `provider = 'manual'`, `verified = false`. A
  centroid dressed as that claim is the false confidence this feature refuses.
- **Remove `barangay` from the mapping rather than leave it and hope.** The
  instruction was explicit and the evidence agreed with it: with no trustworthy
  component, NULL is the honest value. The PSGC cascade stays the only source, which
  means `barangay` is now filled by exactly one mechanism instead of two — the one
  that derives it from a code a person chose.
- **Do not parse the freeform for the barangay.** It would recover Caloocan's
  "Barangay 28" and miss the other three. Leaving it null keeps the three honest, and
  the design already refuses this class of inference elsewhere.
- **Correct the NCR province case in the same pass, but as a recorded fact rather
  than a heuristic.** `Metro Manila` at the province level for NCR is nulled via a
  closed, two-entry set — NCR is the only region in the country without provinces —
  and the correction runs *before* the province→region fallback so the region cannot
  be copied back out of `province`. No name matching, no fuzziness.
- **Keep the four payloads as fixtures, with their freeforms verbatim.** A test that
  asserts `barangay` is null is weak on its own — it passes for a provider that sends
  nothing. Caloocan's fixture asserts *both* that "Barangay 28" is present in the
  payload's own freeform and that `barangay` is still null, so a future restoration of
  the mapping fails loudly with the evidence sitting beside it.
- **Fix the false comment, change no behaviour.** The instruction was to describe the
  actual mechanism without changing behaviour unnecessarily, so the route is
  untouched — only the paragraph. It now names `validate-structured.js`, the derived
  geography, and the pin as the one client-supplied coordinate, which is what a reader
  needs to find the real boundary.
- **Stop at C rather than substituting D.** The TomTom portal permission is the
  blocker and stays the blocker. D would centre on a barangay centroid instead of a
  street, needs a dataset this repo does not have, and is not what was asked for.
  Choosing it silently would have redefined the feature.
- **For the loader, put the detail on the parent reads rather than a new endpoint.**
  The alternative was `GET /api/addresses/[id]`, which would have needed a permission
  covering driver-, route- and settings-readers at once — a union no single
  `requirePermission` expresses. Reusing each parent's own gate invents no permission.
  The cost is that the detail appears in two responses rather than one; the reasoning
  behind it still lives in a single function, which is the part that matters.
- **The loader reports four reasons, not one falsy return.** `no-address-id`,
  `no-psgc-code`, `unknown-barangay` and `unavailable` are genuinely different states,
  and only one of them is a defect. Collapsing them would make the ordinary legacy case
  — the one the design deliberately refuses to guess at — indistinguishable from a bug.
- **A pick identical to what is stored is skipped, not saved.** The registry is
  append-only, so a re-save writes a second row and orphans the first. Opening the
  picker to look at an address should not cost a row.
- **The Google Maps URL paste path stays — ADR-015 wins over #9's first half.** Task #9
  ("remove the Google Maps URL paste path and dead code") was written before
  [[ADR-015 Address Owns Administration, Location Owns The Point]], whose line 168 decides
  the opposite in as many words: the paste path "stays", confined to the two surfaces where
  a location's own coordinates are the operational point. #9 predates it and is superseded
  on that half. Removing it would also have deleted the coordinate-entry path on the
  canonical-location dialog that `src/lib/locations/coordinates.js` was written to protect
  — and `coordinates.test.js` with it.
- **The dead island was deleted; the provider layer behind it deliberately was not.** The
  component (`address-validator.jsx`), its hook (`use-address-search.js`), the map it loaded
  (`address-map-preview.jsx`) and `src/lib/address/validate.js` are gone. Where it stopped is
  the decision: `/api/address/search` and `/api/address/geocode` lost their only client, and
  `provider.js` + `providers/tomtom.js` lost their only callers — but a route is a reachable
  endpoint rather than a dead file, and the provider is what a lifted 403 would use. Open,
  not overlooked.
- **`parse.js` is not part of the island.** Deleting it was the obvious next step and would
  have been wrong: `validate-structured.js` and `invalidate.js` both import
  `emptyAddressValue` from it, so it is live and it carries #30's falsified-mapping fixtures.
  An import check drew that boundary, not an intuition about which files "look addressy".
- **Test the route's attachment, not the loader over again.** `address.service.test.js` already
  covers `loadStructuredAddress`'s four outcomes; doubling it in the route test and asserting
  only what the route does with the result keeps the two files from covering the same ground
  twice while both read as thorough. What the route owns is the contract — both keys always
  present, the right slot, the right reason.
- **Assert key PRESENCE, not just value.** Two of the five use
  `toHaveProperty("structured_address", null)` rather than reading the value and comparing it.
  `expect(body.structured_address).toBeNull()` passes for an absent key and an explicit `null`
  alike, and the difference between those two is the whole thing the route promises: a caller
  must be able to read the value without first checking that the key exists.
- **Pin the locations route's permission in a test — a judgement call worth naming.**
  `route.get.test.js` asserts the handler asks for `routes: read`. An assertion that restates
  the code is usually a tautology, and I nearly left this one out for that reason. It earns
  its place because of who borrows it: the hotel page is gated on `settings: read` and reads
  its address detail through this route, which is safe only while every role holding the
  first also holds the second. Narrowing the permission would break the hotel picker for a
  role no other test names, so that change should fail a test pointing back at the note
  rather than pass unnoticed.

- **Reconstruct rather than drop — and reconstruct all seven object-groups, not just the
  column that was asked about.** Task #20 offered three options; (c) "drop as abandoned" was
  ruled out because `121` is the first of a live end-duty family and removing a column mid-
  development invites a runtime failure in code that still references it. Option (b) — a fresh
  idempotent migration — was chosen, but one covering only `source_inspection_id` would have
  left six other object-groups unbuildable from the files. Shipping it as `130` and not `125`
  was settled by `db:status`, never by reading the directory.
- **The reconstruction is guarded so it cannot damage the database it was copied from.** It is
  derived from residue, and a reconstruction that can write is one that can be wrong
  destructively. Every statement is `IF NOT EXISTS`-shaped, so it is a no-op on live by
  construction, and inertness is *shown* rather than asserted: `db:dump` afterwards produced a
  byte-identical `schema.sql` and `cron.job` still held its four jobs under their real names.
- **Version 130 was applied and then rebaselined, in that order and with the dump in between.**
  Editing the file after applying it changed its checksum, so `db:rebaseline` re-recorded it —
  permitted precisely because the empty `db:dump` had already established that live matched the
  file's intent, which is the precondition the tool's own docstring sets.

- **Delete the address provider layer rather than leave it mounted (task #31).** Two
  alternatives were live: delete only the two routes and keep `provider.js` + `tomtom.js`
  for a future typed-address feature, or keep everything and simply document the 403. The
  first failed on the interface — the library serves the combobox shape the app deliberately
  retired in favour of the PSGC cascade, so it is not the foundation for anything the app
  still wants. The second failed on the standard already applied to `address-validator.jsx`
  the same week: "kept pending the 403" was rejected there as *a reason with no expiry*, and
  the routes are the same argument wearing a route's clothes. A route that can only answer
  `502` is not a reachable endpoint in any sense that matters.
