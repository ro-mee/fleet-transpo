# 2026-08-18

## What I worked on

- Cleared all reservation data from the live DB (fresh-start re-seed path).
  Script saved at `scripts/clean-reservation-data.mjs` (231 requests + their
  dispatch/trip/event/integration-log/notification chains).
- **Closed the sev-2 [[BUG AI Recommendation Can Serve Stale Pair]]** for the
  Reservation Info panel — all eight gaps fixed:
  1. GET revalidates a stored snapshot against live pairing before serving it;
     a stale pair is discarded and regenerated.
  2. The expired-snapshot Regenerate button now sends `regenerate=1`.
  3. Expired / refreshing recommendations disable Accept & Assign.
  4. `saveRecommendationSnapshot()` stores and returns the canonical
     `{ trip, recommended, alternate }` shape (was a flat pair).
  5. Narration is pinned to the selected vehicle/driver via `?vehicle_id=&driver_id=`.
  6. The panel normalizes singular `conflict` vs plural `conflicts[]`.
  7. `markRecommendationConsumed()` runs after a successful assignment.
  8. The recommendation endpoint is the single source of truth.
- **Fixed a false "Fully booked" in the AI-Assisted Assignment dialog.**
  The dialog's no-pair empty state was gated on `!pairingData && isAiLoading`,
  so the availability counts (`vehicleCount` / `driverCount`) could read 0 while
  the slower `/api/vehicles/available` + `/api/drivers` queries were still in
  flight — flashing "Fully booked / 0 vehicles / 0 drivers" even when the live
  endpoints return eligible resources. Gated the empty state on `manualLoading`
  (vehicles + drivers + pairing + substitutes), so a verdict is only shown after
  all availability data has settled. Live endpoints for RS-E9KZ returned 3
  vehicles / 5 drivers; the dialog was wrongly reporting 0/0 mid-load.
- **ROOT CAUSE of the persistent "Fully booked 0/0": a 500 in the availability
  endpoints.** `/api/vehicles/available` and `/api/drivers` both declared
  `const returnAt = returnAt ? new Date(returnAt) : null` inside a block where
  `returnAt` was already an outer binding — a self-shadowing
  `ReferenceError: Cannot access 'returnAt' before initialization` whenever
  `pickup_at` was present and `return_at` was absent (the dialog's call for any
  request without `scheduled_arrival`). Both endpoints 500'd, the dialog loaded
  no data, and it showed "Fully booked / 0 / 0". Renamed the inner binding to
  `returnDate`. Reproduced before (500) and after (200, 3 vehicles / 5 drivers)
  through the real route handlers. → [[BUG Availability Endpoints 500 False Fully Booked]]
- **Removed the "Choose manually" override from the AI-Assisted Assignment
  dialog** (`ai-assign-dialog.jsx`). The dialog now commits only the recommended
  vehicle+driver pair — the dispatcher no longer picks a custom pair inside the
  dialog. Removed the manual picker JSX, its state (`selection`, `showManual`,
  `searchQuery`), the `pinned` useMemo, and the now-unused `Search`,
  `ChevronDown`, `ChevronUp`, `Info` icon imports. This also cleared the
  previously pre-existing `useMemo` conditional-hook lint error (it lived in the
  removed `pinned` block). eslint now reports **zero** problems on the file.
- **`AiAssignDialog` is now a thin shell over the shared `AiRecommendationPanel`.**
  The dialog no longer runs its own vehicles/drivers/pairings/substitutes
  queries or builds its own "Best Available Pair" card — it embeds the SAME
  panel the reservation detail page renders inline, so the advisor, narration,
  regenerate, swap, conflicts and the accept action live in exactly one place.
  The panel owns fetch + assignment; the dialog frames it with guest/route/
  readiness context and forwards `onAssigned` to the caller. Removed the
  duplicate `assignMutation`/`assignError` wiring from both consumers
  (`reservations/[id]/page.js`, `reservations/queue/page.js`).
- **Standard Proper Case for person names** (migration `056_names_proper_case.sql`).
  Added `toProperCase()` in `src/lib/validation` (Title Case: lowercase then
  capitalise each word; handles `O'Neill` and `juan-carlos`). Applied via
  `initcap()` to `employees.first_name/last_name`, `drivers.emergency_contact_name`
  and `transportation_requests.guest_name`. `TEST DRIVER` → `Test Driver`,
  `KARLO RAFAEL SUNGA TORRES` → `Karlo Rafael Sunga Torres`. Left `normalizeName`
  as trim-only on purpose — the drivers email builder derives addresses from
  `normalizeName().toLowerCase()`, and Title-Casing a multi-word name would
  inject spaces into an email. Applied directly (ledger recorded) because
  `db:up` is blocked by pre-existing checksum drift. Added 8 unit tests.
- **Standard Proper Case for vehicle names / manufacturers**
  (migration `057_vehicle_names_proper_case.sql`). Added `toVehicleTitleCase()`
  in `src/lib/validation`: Title Case that (a) turns a hyphen into a space
  (`TEST-VEHICLE` → `Test Vehicle`), (b) keeps known vehicle-type acronyms
  uppercase (`SUV` stays `SUV`), and (c) leaves digit-bearing model identifiers
  verbatim (`CiviC18S`). Applied to `vehicles.vehicle_name` and `.manufacturer`.
  The `model` column is deliberately NOT title-cased (model codes like `SVJ`,
  `CiviC18S` are identifiers). Plates were already ALL CAPS and are left
  untouched (normalizePlate). Wired `toVehicleTitleCase` into both vehicle
  create/update routes so new input is normalised on write. Changed the
  fleet-grid "Unknown" manufacturer fallback to "Unassigned". Added 6 unit
  tests. Applied directly (ledger recorded) — `db:up` is blocked by drift.
- **Fixed the driver self-service work schedule not loading on the web.**
  The `/api/driver-work-schedules` GET read the caller's role as
  `session.user?.roles?.role_name`, but a NextAuth web session exposes a FLAT
  `session.user.role` (the nested `roles.role_name` shape only exists on the
  client, where `useAuth()` returns the employee row). So for a web driver the
  `role === "driver"` branch never ran, `driverId` was never resolved from the
  session, and the endpoint fell through to a `400 driver_id is required` — the
  driver's self-service schedule page showed "No weekly schedule on file yet"
  even when a schedule existed. Fixed to read `session.user?.role` (consistent
  with `requireAuth`). Reproduced before (400) and after (200 + 7 days) through
  the real route handler with a driver session. The `/api/driver/leave` and
  `/api/driver/balances` endpoints already read `session.user.driverId` and were
  unaffected.
- **Google Maps "View on Google Maps" button on incidents.** Added an exact-location
  button to incident rows in both `incidents/page.js` (fleet registry, in the
  Incident Type cell) and `driver/incidents/page.js` (driver self-service list).
  It opens `https://www.google.com/maps?q=<lat>,<lng>` in a new tab so a
  dispatcher or driver can instantly share the precise coordinates with 911 /
  ambulance / roadside assistance. Only renders when the incident has
  `latitude`/`longitude`; incidents saved as a text-only location (no coords)
  show no button.
- **Incidents: stop truncating long location/description text.** The fleet
  registry incident-type cell had `truncate max-w-[200px]` on location and
  `line-clamp-2 max-w-[300px]` on description, and the DataTable cells use
  `whitespace-nowrap` — so long incident details were cut off. Removed the
  truncation and set the incident-type column to `whitespace-normal min-w-[260px]
  align-top` so full location and description wrap and are visible. Also removed
  the `truncate` on the driver self-service incident list (type/description/
  location now show fully).
- **Incident coordinates: normalise DMS / URL / decimal into one decimal pair.**
  Incidents could store the driver's position as a DMS string
  (`14°45'06.1"N 121°03'26.3"E`), a Google Maps URL, a `"lat, lng"` decimal
  string, or the decimal lat/lng columns — and the Google Maps "share for 911"
  button only worked when the decimal columns were populated, so a DMS-located
  incident showed no button (and a DMS string alone is hard to share). Added
  `src/lib/geo/incident-coords.js` (`resolveIncidentCoords`) which resolves all
  four shapes to a single decimal pair, and wired it into both incident pages so
  the "View on Google Maps" button always opens a clean decimal `?q=lat,lng`
  link. DMS → `14.751694, 121.057306`. 8 unit tests, lint clean.
