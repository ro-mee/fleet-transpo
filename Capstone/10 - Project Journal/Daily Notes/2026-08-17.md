# 2026-08-17

## What I worked on

- Traced AI-assisted assignment from candidate scoring through UI display and
  the final assign endpoint.
- Verified live data for `RS-5RB7`: `XYZ 5678` belongs to Jack Mors (driver 21)
  and has no substitute schedule, so the displayed Juan Dela Cruz pair was invalid.
- Removed the assignment dialog's fallback to stale AI vehicle/driver JSON and
  forced the active custodial-pair query to refresh when the dialog opens.
- Audited the separate AI Recommendation panel inside Reservation Info.
- Recorded the remaining work in [[BUG AI Recommendation Can Serve Stale Pair]].

## What I learned

- A deterministic scorer is not enough if the UI combines it with a stale
  identity source.
- Recommendation snapshots must be revalidated against live pairing data before
  display, not only when the user commits them.

## Problems encountered

- The assignment dialog and Reservation Info panel use different recommendation flows.
- The Reservation Info panel has stale/expired snapshot, regenerate, payload-shape,
  narration-cache, conflict-response and snapshot-consumption gaps.
- ESLint still reports the pre-existing conditional `useMemo` error in
  `ai-assign-dialog.jsx`.

## Decisions made

- A vehicle-driver pair is valid only when backed by the current active custodian
  or an explicit substitute covering the pickup date.
- Stored AI JSON is advisory metadata and must never supply fallback assignment ids.
- The server recommendation endpoint should become the single source of truth for
  the Reservation Info panel.

## Next steps

- Revalidate or discard recommendation snapshots before returning them.
- Normalize persisted and live payloads to `pair.recommended` / `pair.alternate`.
- Fix regeneration, narration keys, conflict rendering and snapshot consumption.
- Add focused regression coverage for stale custodial reassignment.
