# 2026-09-18

## What I worked on

Two threads: the web session idle timeout, and the mobile in-app guide.

### Web — made the session idle timeout real, then tightened it 1 hour → 5 minutes

Started as an analysis question — "how does session expiration work, and can we cut it to 5 minutes?" — and turned into a security finding. The dashboard advertised a 1-hour idle timeout that **could not fire**. `resolveCurrentIdentity()` slid `web_sessions.last_seen_at` on any authenticated request older than 5 minutes, with no check for human activity. Every dashboard page polls continuously (sidebar counts every 30s, live map 15–30s, dispatch plan 10s, two with `refetchIntervalInBackground: true`), so an abandoned browser refreshed its own deadline roughly every 5.5 minutes. Only the 12-hour absolute cap was ever enforced.

Fixes:
- Deleted the auto-slide. `POST /api/auth/heartbeat` is now the **only** writer of `last_seen_at`, and the client gates it on real DOM events.
- New `src/lib/auth/session-policy.js` — a dependency-free module both client and server import, so the numbers can't drift apart again. The warning window and heartbeat interval are *derived* from `IDLE_TIMEOUT_SECONDS`.
- Idle timeout → 300s (migration `113_session_idle_timeout_5min.sql`, no backfill).
- Modal: derived the hardcoded "1 hour" copy, fixed the dead exit animation (early `return null` was unmounting `AnimatePresence`), added autofocus to "Stay signed in".
- Routes the mount/visibility 401s into the expired modal — they were being swallowed.

### Mobile — the Driving Safety Lock did not exist, and five other guides mispresented

I was asked to analyse how the in-app guide works and whether the "6 + 1" guides actually show what they claim. Read-only first: the milestone definitions (`mobile/lib/coach-marks.js`), the provider, the target wrapper, the overlay, and every trigger call site.

The headline finding is that the **Driving Safety Lock was doubly inert**. `CoachMarkProvider` declared `isDriving = false` as a prop and guarded on it, but the only render site — `mobile/app/(app)/_layout.js` — passed `driverId` alone. So the guard could never fire. The context value didn't expose `isDriving` either, so `DriverSos.js`'s `!isDriving` check destructured `undefined` and its "only once stationary" delay was a bare 2-second timer. Meanwhile the feature doc §7.1 specified suppression above 10 km/h and §9 ticked it off as done.

Five more, all found by reading rather than running:

1. **Guides pre-empted each other.** Home mounts and shows the Welcome card; ~2 s later `DriverSos` fires `triggerMilestone("sos")` and replaces it. The greeting was never read *and* never marked complete, so it only ever appeared on a second launch. Same race let `pretrip_complete` cut off an open `pretrip_remarks`.
2. **Spotlights could point at nothing.** `trip/[id].js` and `fuel-report.js` wrapped targets in ScrollViews but never passed the `scrollRef` that `CoachMarkTarget` needs to scroll them into view.
3. **The spotlight geometry animation was dead code.** `CoachMarkOverlay` animated `animX/animY/animW/animH` for 240 ms — then rendered the raw `spotX/spotY/spotW/spotH`. So a re-measuring target snapped instead of moved.
4. **Duplicate `targetId` ownership.** `inspection.remarks` mounts once per failed item. Two FAILs registered one id (last-measure-wins), and unmounting *either* deleted the shared registration.
5. **Copy had drifted from the spec** in the Welcome and Offline cards.

## What I learned

**A timeout constant is not a timeout.** The policy was documented in three places and enforced in none. The number was right; the write path was wrong. Reading `IDLE_TIMEOUT_SECONDS` would have told me the policy and told me nothing about whether it held.

**Deriving constants is the actual fix.** The dangerous part of a naive `3600 → 300` change is that three unrelated values were all "300": the client warning window, the server slide throttle, and the (new) idle timeout. Set the timeout to 300 and the warning window *becomes* the entire timeout window — the modal appears at login and never dismisses. The derived values plus the invariant tests are what stop that class of bug, not the constant change itself.

**A gate that is never reached looks identical to a gate that is never tripped.** Both the web timeout and the mobile lock were "implemented" and did nothing. Neither failed loudly. The web one needed a read of the write path; the mobile one needed a read of the *call site* — the prop existed, the guard existed, and only the wiring was missing. Static analysis found both; no test would have, because the tests asserted the constants and the definitions, not that anything was connected.

**"Never pre-empt" is not obviously safe.** My first version of the one-guide-at-a-time rule blocked any trigger while *a* milestone was active. Reading it back, that wedges the app: navigate away from an open guide and it stays active but invisible, offering nothing to dismiss, refusing every later guide forever. Scoping the guard to what is **on screen** rather than what is *active* fixes both the original race and the wedge I would have introduced. The ref mirror also had to be written during render, not in an effect — effects run child-first, so a trigger fires before the provider's own effect could clear a stale owner.

**Two independent facts are needed to make a spotlight honest:** the target must be registered *and* on screen. The old code checked only the first, so a target scrolled out of view measured positively and the overlay dimmed the entire screen with the cutout framing nothing.

**Safety gates must be re-checked after every await.** Opening a mark reads `AsyncStorage` asynchronously. Checking the lock only before that read lets a vehicle that starts moving *during* it get a mark anyway.

**Hand-verification held up, and that's worth knowing precisely.** Blocked from executing anything, I traced all 11 motion-state tests by hand against the source and confirmed every structural assertion string existed verbatim. When the run finally happened, all 50 mobile tests passed with no surprises — the traces were right. That's a genuine result about the technique: reading catches mistyped assertions, shifted strings, bad import paths and boundary off-by-ones reliably. But it was never going to catch a syntax error in a `.jsx` file or a broken module graph, and the fact that it happened to be sufficient *here* doesn't make it a substitute. The reason it held is that these particular tests are assertions about text and arithmetic, which is exactly what reading verifies well — and it is exactly what the tests that *can't* be hand-verified this way (the rendering of the provider) are not.

- **`schema.sql` cannot review an RLS migration.** AGENTS.md calls the schema.sql diff "the review artifact", but the file contains zero policies — the only match for "POLICY" is `policy_version`, a column. So for `114_app_errors_rls.sql` and `115_rls_gap_tables.sql` the diff proves nothing either way; only a `pg_policies` query against live would say. That leaves the RLS gap a genuinely open question rather than a settled one, and I have said so in the notes rather than letting the diff imply coverage it doesn't have.
- **The apply does less than it looks like.** The default only governs rows that omit the column, and `src/lib/auth.js:145` passes `IDLE_TIMEOUT_SECONDS` explicitly on every INSERT — so sessions created after the apply idle at 300s, while sessions already live keep their stored 3600 (`src/lib/api/utils.js:80` reads the row value) and idle at 60 minutes until they roll off inside the 12-hour cap. That is the migration's stated intent — the alternative is a mass logout at deploy time — but it means the 5-minute policy is not fully in force for up to 12 hours.
- The Impeccable design hook flagged `design-system-font-size` three times on `sm:text-[1.75rem]` in the session modal, and four literal colours (`#000`, `#111`, `#ddd`) in `fuel-report.js`. - `npm run lint:ci` was red — 6 `react-hooks` warnings, all attributable to this work. Four were mine in the coach-mark components and are fixed properly: two render-time ref writes in `CoachMarkProvider.jsx` moved to `useLayoutEffect` (which flushes synchronously at commit, before a pending async continuation can read a stale value — the same guarantee the render-time write existed for, in the sanctioned place), and the per-instance token in `CoachMarkTarget.jsx` moved from a ref to a lazy `useState`, since it is read during render and belongs in two dep arrays. The fifth, `if (isDriving) abandonActiveMilestone()` in an effect, carries a documented `eslint-disable-next-line`: the render-derived alternative would change safety behaviour, and I would rather suppress a heuristic than rewrite a lock I cannot exercise on a device. The sixth, in `src/context/session-manager.jsx`, is a genuine false positive — `syncSession`'s first statement is an `await fetch`, so every setState in it runs after a network round trip, never synchronously in the effect body — and is suppressed with that reasoning recorded inline.

## Decisions made

- **Web idle timeout: 5 minutes** (not 30/15). Aggressive for this workload; reversed by changing one constant plus the migration default.
- **Strict enforcement** — heartbeat-only, no auto-slide, no non-GET safety net. The safety net was rejected because it would let an hour of read-only work count as activity.
- **No backfill in 113.** Rewriting live rows to 300 would instantly idle-expire every session older than 5 minutes — a mass logout that presents as an outage.
- **Web only for the session work.** The mobile refresh-family absolute cap is out of scope; it touches the rotation transaction and replay-revocation path.
- **Mobile motion comes from the existing 30 s GPS poster**, not a second watcher. It already reads `loc.coords.speed` on every fix and already owns a module-level pub/sub. No extra battery cost.
- **A 2-minute sticky hold, not the latest fix.** Positions arrive every ~30 s, so a latest-fix-only check would un-suppress tips at a red light or in a tunnel — exactly when the driver is still driving.
- **Unknown motion fails open.** No permission, tracking off, or no fix yet all read as stationary, so the guide still works on a device that never grants location. The lock engages only on positive evidence. The cost, stated plainly: a driver who has denied location keeps getting tips while moving.
- **The threshold is `10 / 3.6` m/s.** `LocationObjectCoords.speed` is metres per second; the spec is in km/h. A bare `10` would have put the gate at 36 km/h.
- **Abandoned, not completed.** A mark the lock takes away is not written to storage, so it returns when the vehicle stops instead of being burned unseen.
- **All six gaps fixed**, per the approved plan — not just the safety one.

Two deviations from the approved plan, both because the plan as written would have left a defect:

- **`trip_readiness` is now gated to pre-start trips.** The plan said only to drop the `targetId` from the underway branch (the spotlight framed a "this trip is underway" line while the copy explained when a trip *can* begin). But all three of that milestone's steps target controls that exist only in the pre-start presentation, so dropping the id alone would have left the overlay hidden with the milestone active and unable to complete — and once a guide can no longer be pre-empted, that blocks every guide after it. Underway trips are `live_trip`'s job.
- **The non-pre-emption guard is scoped to *visible*, not *active*.** Explained under "What I learned" — the plan's rule as literally written wedges the app after navigation.
