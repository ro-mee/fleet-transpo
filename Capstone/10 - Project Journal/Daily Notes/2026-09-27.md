# 2026-09-27

## What I worked on

Finished task #27 — the end-to-end verification of the driver address migration, run
against driver 60. The whole runbook is now green: the address prefills from the
server, the cascade reopens on a saved address, a rename-only edit leaves it alone,
and a placed pin is stored.

The last item was the one that had been failing for days: the residential pin. It
turned out not to be a migration problem at all. The address dialog's submit button
was also submitting the page's form, so "Use this address" saved the driver
immediately — before the pick it had just made had reached React state. The page
wrote the address back unchanged, showed a green success, and the pin was never sent.

One line in `address-form-dialog.jsx` (`event.stopPropagation()`) and it works.

Then task #29 — the pin map now centres on the address as you pick it, instead of
opening on the whole Philippines. The `ph_*` tables have no coordinates at all (they
are a hierarchy, not a gazetteer), so the centre comes from a TomTom lookup with the
public key, straight from the browser. It moves the viewport and never the pin.

Verified in the browser at the end of the day: picking a barangay centres the map and
places no pin, changing the city returns it to the country view, and reopening an
address that already has a saved pin leaves the view on the pin.

Then closed the gap that verification exposed. `SyncView`'s ordering was backed by
nothing but those four observations, and could not be tested where it lived — the file
imports Leaflet at module scope and no node test can load that. The decision moved to
`src/lib/address/pin-view.js` as a pure `planViewMove`, with 13 tests over the ordering;
the component now only performs the `setView` and holds the two refs. The four browser
checks predate the move, so three of them were repeated afterwards — centred with no pin,
on the pin, country view — all matching, which is what lets this be called
behaviour-preserving rather than assumed to be.

Then the two latent defects filed this morning rather than fixed. The driver edit
form keyed its reset effect on the `driver` **object** instead of `driver_id`, and
React Query hands back a new object for the same row on every refetch — so the reset
ran after every save, on every window refocus, and on every reconnect. `form.reset()`
on the post-save refetch reinstates the server's values, which means anything typed
while the save was in flight was overwritten, and any address picked on that visit was
thrown away. Silently, both. A `seededDriverId` ref now decides whether to seed, and
the same edit corrected the comment that still described the pre-`loadStructuredAddress`
picker. Lint clean; **no browser check was run**, and none could be — the page renders
React and this repo has no component test harness.

Last of the four, and the one the other three kept pointing back at: the
unchanged-pick silence. `isUnchangedPick` refuses to submit an address equal to the
one already saved, which is correct — the `addresses` registry is append-only, so
re-saving an identical address writes a second row and detaches the one the record
was pointing at. What was wrong was that the refusal was **invisible**: the dialog
closed and nothing on screen changed, so "already saved" and "my change was lost"
looked identical. Not a cosmetic complaint — it is the exact shape that concealed
the pin bug for three days, a static fingerprint and a silently dropped pick while
every surface reported success. The skip stays; it now says so. **The filed entry
cited one call site and there were three**: the shared picker, plus inline copies in
the hotel-base settings and the canonical-location editor — two hand-written versions
of the block the shared picker exists to replace.

Last of the day: the entry that had been sitting at the bottom of the "what this does
NOT fix" list since the migration started, and the one the other four kept pointing
back at. `verify-driver-addresses.mjs` could see what `drivers.address_id` **pointed
at** — the chain, the codes, the two ids — and could say nothing at all about the rest
of the `addresses` table. The registry is append-only, so a row written and abandoned
is permanent, and the runbook's step 1 writes rows into the live project. The script
could not prove the pass wrote only what it meant to, and should not have been read as
if it could.

What decided the shape was noticing that **an orphan is not a defect**. Replacing an
address legitimately orphans the row it replaced — that is what append-only means here.
So a check that went red on any unreferenced row would go red on a healthy database the
first time anyone edited an address. But a save that inserts a row and never repoints
the referrer leaves an orphan too, and that is a real defect — and **one run cannot tell
those apart**. So this reports instead of asserting, and the thing that separates the two
causes is a **re-run**: note the ids, make the change, look again. That is the mechanic
the script already uses for the rename fingerprint, so it is one idea in the file rather
than two.

Two smaller decisions fell out of it. The referencing columns are read from
`pg_constraint` rather than written into the script, because a hardcoded list that misses
a column makes that column's rows look orphaned — a false alarm, which is the direction
that wastes someone's afternoon. And a composite foreign key over `addresses` is refused
rather than computed: a per-column `NOT EXISTS` over a pair matches on one column of the
key, which over-counts referrers and therefore **hides** orphans — the direction that
reports "clean" when it is not. Neither exists today; the code says so rather than
printing a number that could be wrong that way.

Then ran it, because a diagnostic nobody has executed is a draft. All 31 checks passed,
and the registry block answered: **12 rows, 6 referenced, 6 not** — ids 5, 7, 8, 9, 10,
11. That is a healthy number and reads as one once you look at the timestamps: 7 through
11 land inside a 40-minute window on 2026-09-26, which is what a repeated save leaves
while someone is chasing a defect, and id 5 shares its timestamp with 6 to the
millisecond, so the step-1 driver creation wrote both. Consistent with replacement — and
deliberately not claimed as replacement, because the report's whole point is that both
causes are identical in one run. The ids are on record now so a later run can attribute
any new one.

**And running it found a bug that reading it had not.** Two passing checks printed the
stored latitude/longitude in their detail strings, and neither was marked `sensitive`, so
`--quiet` printed both. That is the flag's contract broken in the direction that does
harm: `--quiet` exists so this output can leave the terminal, and it withheld the street
address while printing a coordinate — a home location at seven decimals, which is the
*more* precise disclosure of the two. Second time this exact idea has failed in this file.
The 2026-09-25 break printed the address inside the PASS details; this one printed the
pin. Both times the flag was checked against the block it was written for and never
against the per-check details, where there is one line per column and no single place to
look. Fixed by presence reporting (`lat=set lng=set`) rather than by marking them, since
the checks are about presence and the number answered nothing.

## What I learned

**A React portal moves a subtree in the DOM, not in the React tree.** React
dispatches events along the fiber tree, so a form rendered in a portal to
`document.body` still has the *caller's* `<form>` as an ancestor handler. Reading the
rendered markup tells you the opposite, which is why three days of reading markup
settled nothing.

`preventDefault()` and `stopPropagation()` are not interchangeable and neither is
"safer": `preventDefault` stops the browser's default action, `stopPropagation` stops
other handlers hearing the event. This bug needed the second one, and the first had
been sitting there the whole time looking like it had the problem covered.

**Ask what the user sees, not what the code says.** Two hypotheses died to a single
question about appearance (the map renders real tiles; the form's completeness was
visible). The instrument that finally worked was not a better log — it was noticing
that I kept asking for the browser console and kept getting the terminal, and changing
where the diagnostic went instead of asking a fourth time.

**A 403 was hiding a choice, not just a blocker.** I had been treating the TomTom
Search 403 as a wall in front of task #29. It was only ever the *server* key's
permission. The browser key had been searching all along, and it was already in the
client bundle because the map tiles use it — so "blocked" was the wrong word for
something that was really "pick which key, and accept the privacy cost of the one
that works today." Worth remembering: before reporting a blocker, check whether it
applies to the whole capability or just the path I had assumed.

**The wrong-instrument lesson repeated, and that is the part worth keeping.** Verifying
#29, I asked for the browser's Network panel three times and got the dev server log
twice and the console once. None of them can ever show the answer: the lookup goes from
the browser straight to `api.tomtom.com` and never routes through Next.js, so it is
*structurally* absent from every log the server emits. What finally worked was pointing
at the line of text the change already renders under the map — four sentences, one of
which is on screen at all times. Same lesson as the pin bug, one day later: when the
same request keeps coming back as the wrong thing, change where the diagnostic surfaces
rather than asking again. A lesson that has to be learned twice was not learned.

**A yes/no verification question can mean two opposite things.** I asked "was there a
pin marker on the map?" and got "yes". Read literally that is a failure — the feature
would have been placing pins, violating the invariant the whole task is built around —
but it almost certainly meant "yes, no pin, as you described". Guessing either way was
unacceptable: one reading ships a broken invariant, the other blocks a finished task.
The question was the defect, not the answer. Ask for the observation ("was a marker
visible, or not?") rather than a polarity, because a polarity only carries information
if the question was unambiguous and I only find out it was not when the answer arrives.

**A failing test is a claim about the code, not a finding about it.** Twice while
building this the test was wrong and the implementation was right — first a payload
helper that built a viewport twice the size it claimed, then an assertion that a
malformed centre on mount sends the map to the country view, when declining to move is
correct on mount. Both times the reflex to "fix" the code would have introduced a real
bug to satisfy a mistaken expectation. What the second one turned on is worth keeping:
the test's own name said the guard stops a bad centre reaching `setView`, which is true,
and said nothing about where the map should go — the second half was me asserting a
requirement the guard never had. Read the test's name before believing the test.

**A filed bug's call-site count is a claim, and it can be wrong in the direction that
makes a partial fix look complete.** The entry for the unchanged-pick silence said
`isUnchangedPick` was "the only silent exit in `address-picker-field.jsx`" — true as
far as it went, and it named a file rather than a count, which reads as thorough.
There were three call sites: the shared picker and two hand-written copies of the
same block in other pages. Fixing the component alone would have closed the ticket,
left two surfaces silent, and left the record asserting they were fine. The general
shape is worth keeping: when a bug is filed against a **function**, grep for the
function rather than for the file the report mentions, because a shared helper's
blast radius is not visible from the place it was noticed.

**A gate that cannot fail is not a gate.** `Bugs.md:362` records that this repo has
no import resolution in any gate — after a symbol was deleted, eslint and vitest both
passed while three modules still imported it. This change added exactly that shape: one
new export, three importers. So the lint run was not evidence for the thing most
likely to be wrong with it. What settled it was reading all four occurrences and
confirming one definition and three identically-spelled importers. Worth remembering
which way round this goes: the cheap check was the one that could actually fail, and
running the expensive one first would have felt like more rigour while proving less.

**A gate that fails on correct behaviour is worse than no gate.** The orphan check
could have been written as an assertion — "no unreferenced rows" — and it would have
been red within a day of anyone using the feature, because replacing an address
*always* leaves the old row behind. A monitor that cries wolf on the happy path is
one people learn to click past, and then it is silent on the day it is right. The
version that shipped reports, and says in its own output which two causes it cannot
tell apart. The instinct to make a diagnostic decisive is worth resisting when
decisiveness is not available: the honest version of "I cannot answer that from here"
is a sentence, not a green tick.

**When one measurement cannot separate two states, the missing instrument is a
second measurement — not a better first one.** Orphaned-by-replacement and
orphaned-by-a-failed-save are the same observation. No amount of care in a single
query distinguishes them, and I spent a while looking for a column that would (there
is none — the table has no history, only what is there now). What resolves it is
comparing two runs around a change somebody deliberately made. Same shape as the
rename fingerprint already in the file, and the same shape as the pin bug: the
evidence was never in one screen. Worth reaching for the diff sooner when a question
resists a single answer.

**A privacy flag is only as good as the least-considered column, and the column
nobody considers does not read like the thing being protected.** `--quiet` exists to
stop a home address leaving the terminal. It withheld the street text and printed the
pin — seven decimal places, a more precise home location than the address it was
hiding. Nobody overlooked `formatted_address`; it is literally named "address". What
was overlooked is that a coordinate is one too, and that is the whole failure: the
review asked "is this an address?" and the right question was "what is the most
revealing column on this table, and does this line touch it?". Worth keeping for any
redaction, allowlist or log filter — audit it against the data, not against the
vocabulary.

**Running the tool is part of building it, and the bug it finds may not be the one
the tool is about.** The registry block worked exactly as designed on its first live
run — and the run is also what exposed the coordinate leak, which no amount of
re-reading the diff would have shown, because the defect was in output I had to see
rendered to notice. I had written three paragraphs in `Bugs.md` about what the run
could not tell me, and the thing it actually told me was something else.
"Verified by reading" and "not yet run" are different states, and the gap between
them is where this was hiding.

## Decisions made

- Kept the two verifier checks added by the dead "incomplete form" hypothesis (house
  number, street). The picker demands a house number the server does not, so a valid
  row can still seed a form that looks complete with one required field empty — a real
  gap, found by accident, worth keeping.
- Filed rather than fixed, and then fixed the same day: `edit/page.js` keyed the form
  reset on the driver *object* rather than `driver_id` — and it did fire, on the
  post-save invalidation, where it could discard anything typed while the save was in
  flight; and `edit/page.js` still documented the behaviour the
  `loadStructuredAddress` work replaced. Both closed in the last pass of the day; the
  first is the one with real user impact.
- Last of the four, and the one the others kept pointing at: `isUnchangedPick` drops a
  pick it judges unchanged with no feedback at all. The skip is right — the registry is
  append-only, so re-saving an identical address costs a row and detaches the one in
  use — but closing the dialog in silence is what concealed the pin bug for three days.
  Kept the skip, added the line. **The filed entry named one call site; there were
  three** — the shared picker plus two hand-written copies of the same block.
- Standard for this surface: every diagnostic prints booleans or key **names** only,
  never a value. An address is a real person's home and a debug line is the easiest
  place to leak one. All five `[addr-debug]` sites are removed.
- The orphan check is a **report**, not a check — decided against the obvious
  alternative. A failing check on any unreferenced row would be red on a healthy
  database, since replacing an address always orphans the row it replaced. The two
  causes are indistinguishable in one run, so the script lists the ids and says what
  they could mean, and the comparison that attributes them is a re-run. It prints
  under `--quiet`, because it selects ids, timestamps and PSGC codes and never
  `formatted_address` — the flag exists for stored address text, and hiding the
  finding exactly when the output might travel would be backwards.
- The referencing columns come from `pg_constraint` at run time rather than a
  hardcoded list. A stale list is wrong in the direction that invents orphans —
  it would send someone hunting a defect that is not there. `schema.sql` was itself
  five migrations behind live on 2026-09-25, so "read it from what is running" is
  not a style preference here.
- The coordinate leak is fixed by **presence reporting** (`lat=set lng=set`) rather
  than by marking the two checks `sensitive`. Both would have worked; the standing
  rule for this surface already says booleans or key names, never a value, and the
  checks are about presence anyway — `chk_addresses_coords_pair` makes a half-pair
  unstorable, so `lat=set lng=NULL` answers everything the number did. Marking them
  would have kept the numbers in the output and made the flag's scope a thing to
  remember rather than a thing that holds by construction.
