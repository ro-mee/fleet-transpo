### Diagnosed the `admin@gmail.com` login failure (no code change)

Reported as "can't log in as `admin@gmail.com` / `Admin123!`". The login page
answers *"Incorrect email or password. Please check and try again."* — which is
only reachable when `authorize()` returns `null` (`src/app/(auth)/login/page.js:944`,
after NextAuth collapses every failure to `CredentialsSignin`).

Root cause, confirmed against live with
`node --import ./scripts/alias-loader.mjs scripts/audit-otp-inbox-ownership.mjs`:

- **`admin@gmail.com` is no longer attached to any employee row.** The email-OTP
  rollout moved employee 48 onto `crypticalrome@gmail.com` —
  `scripts/soft-delete-otp-collision.mjs` releases that address from employee 7
  (retiring it to `deleted-employee-7@example.com`) and then overwrites employee
  48's `email` column outright. Nothing reassigns `admin@gmail.com` afterwards.
- So the Credentials lookup (`WHERE email = $1 AND status='Active' AND
  deleted_at IS NULL`, `src/lib/auth.js:53-59`) finds nothing, bcrypt runs against
  the dummy hash, and the login dies **before** the second factor. That is why no
  OTP modal appeared.
- `Admin123!` is not the password either: migration `008` seeded `admin123`,
  migration `061` NULLs that hash where it still matches, and the live admin
  password was rotated (`Authentication.md:136`). The string `Admin123!` appears
  nowhere in the repo.

**Live state (2026-09-23):** 36 active accounts — **0 owned, 17 unverified,
19 unreachable**. Employee 48 (`admin`) = `crypticalrome@gmail.com`; employee 8
(`super_admin`) = `lorenteromejoseph@gmail.com`.

**Live state after the cleanup (same day):** **17 active accounts** — ownership

### Built the optional biometric app lock on mobile (no backend change)

Added an **optional, off-by-default** biometric application lock to the driver app,
in the same shape as a banking app's app-lock. It is not a login: it gates the local
UI, and password + the emailed OTP remains the only way to create a session.

The gap it closes: `AuthProvider` (`mobile/lib/auth.js`) restored a session on cold
start from `fleetops_access_token` + `fleetops_user` alone — no credential
re-presented, no server call. A phone picked up, handed over, or left on a depot
bench exposed the whole driver UI for up to 30 days.

- **New**: `mobile/lib/app-lock.js` (+ test), `app-lock-context.jsx`, `biometric.js`,
  `biometric-method.js` (+ test), `biometric-errors.js` (+ test),
  `components/AppLockScreen.jsx`, `components/AppPrivacyVeil.jsx`,
  `app/(app)/profile/security.js`.
- **Modified**: `lib/auth.js` (sign-out clears biometric), `app/_layout.js`,
  `app/(app)/_layout.js` (the gate), `(tabs)/profile.js` (new row),
  `app/login.js` (post-login offer), `app.json`, `package.json`.
- **Nothing under `src/**`. No migration. No new route.** `verify:auth` and
  `db:status` must both come back unchanged, which is the point.

The design decision worth recording is **what is *not* stored behind the gate**. The
obvious move — put the refresh token in a `requireAuthentication` SecureStore item —
fails on this platform in both directions:

1. Android puts the keystore key behind `setUserAuthenticationRequired(true)`, which
   gates **writes** too, so re-sealing a copy after each 15-minute rotation would
   prompt the driver every 15 minutes.
2. Re-sealing only at lock time hands back a *superseded* token, and refresh rotation
   is single-use with replay wiping the whole family — unlocking would sign the driver
   out.

So the gated item holds a **non-secret unlock sentinel**. Reading it *is* the
assertion, because the OS refuses the read until it has authenticated the driver. The
refresh token stays readable, which is also what keeps background trip GPS alive while
locked. The honest description is therefore **an OS-enforced application lock, not
encryption of the session token** — and that is written down in the code, the docs and
the threat model rather than glossed.

Enrollment changes turned out to need no code: iOS `biometryCurrentSet` invalidates
the item the moment the enrolled set changes, so adding a fingerprint to a seized but
unlocked phone does not open FleetOps. A settled read returning `null` is treated as
`CREDENTIAL_INVALIDATED` — lock off, session kept, password path.

Both native packages are installed (`expo-local-authentication@17.0.9`,
`expo-screen-capture@8.0.x`). I read the *installed* typings rather than trusting the
docs, and that check earned its keep — three things it caught:

1. **`unavailable` is not a real error code.** The `LocalAuthenticationError` union has
   `not_available`; the map keyed on `unavailable`, so a genuinely unavailable sensor
   fell through to the generic message. Now mapped, and a test asserts on the full union
   so the next drift fails loudly instead of quietly degrading.
2. **`canUseBiometricAuthentication()` is synchronous**, not a promise — my `await` was
   harmless but the comment describing it was wrong.
3. **Android's `biometricsSecurityLevel` defaults to `'weak'`**, admitting Class 2
   camera face unlock. `canUseBiometricAuthentication()` requires a *sufficiently secure*
   enrollment and `getCapability()` consults it, so a weak-biometric-only device cannot
   switch the lock on at all. Recorded in [[Security Audit]] as a limit that is closed
   deliberately rather than one that never existed.

The same read confirmed the claim the whole enrollment story rests on: `requireAuthentication`
really does map to iOS `biometryCurrentSet` and Android `setUserAuthenticationRequired(true)`
(SecureStore 15.0.8 typings, `SecureStoreOptions.requireAuthentication`).

### The dev client crashed on first launch — and it was a one-word bug

The rebuilt dev client installed and then died immediately:

```
ERROR  [Error: Element type is invalid: expected a string (for built-in components) or a
class/function (for composite components) but got: undefined. You likely forgot to export
your component from the file it's defined in, or you might have mixed up default and named

```

Cause: `components/AppPrivacyVeil.jsx` exports **only** a default
(`export default function AppPrivacyVeil()`, `:28`), but `app/_layout.js` imported it as a
**named** import:

```js
import { AppPrivacyVeil } from "../components/AppPrivacyVeil";  // → undefined
```

Undefined as a JSX element type is exactly that error, and `ThemedApp` is where the veil is
rendered. One word — the braces. Now `import AppPrivacyVeil from ...`, matching how
`AppLockScreen` is imported in `(app)/_layout.js`.

I checked every other new export/import pair in the same pass: `biometric.js`,
`biometric-errors.js`, `biometric-method.js` and `app-lock.js` are named-only and imported
named; `app-lock-context.jsx` is named (`AppLockProvider`, `useAppLock`) and imported named;
`AppLockScreen.jsx` and `app/(app)/profile/security.js` are default and imported default.
`AppPrivacyVeil` was the only mismatch.

**Why nothing caught it, and what that says about the gates above.** The root lint setup is
ESLint 9 + `eslint-config-next` with no `eslint-plugin-import`, so `import/named` — the rule
that exists for precisely this — is off. The unit tests never render `app/_layout.js`, and
this is a `.js` file, so no type checker saw it either. It needed the app to actually start.

That is a correction to the story I told myself three paragraphs earlier. I had written that
lint caught the third defect reading had missed, and that this was the argument for running
the gates even when the code looks right. True, and still not enough: the gates I *could*
run were structurally blind to this one, and the single gate I could not run — a real device

evidence that a screen renders.** I had also written, in the audit page, that this feature
"cannot affect what the app does at runtime" because nothing under `src/**` changed; that
was true of the *backend* and I let it drift into sounding like a claim about the app.

The fix is JavaScript only, so the existing dev client reloads it — no new build needed.

### Built the system-wide address registry — foundation only, no surface migrated (code + migration)

Started the reusable address/location system: **one** address field for the whole app,
with autocomplete, explicit selection, coordinates, structured components, postal code, a
map preview and server-side validation. Migration `122_address_registry.sql` (`addresses`)
is applied and the library, both API routes and the component exist and are verified.
**No address form in the app has been migrated yet**, deliberately — see the end of this
section.

The decisions that shaped it:

- **One normalized `addresses` table, not a lat/lng pair per entity.** `locations`,
  `drivers`, `drivers.emergency_contact_address_id` and
  `transportation_requests.pickup_location_id`/`dropoff_location_id` point at it.
  `locations` keeps its own `address`/`latitude`/`longitude` as a **maintained
  denormalization** for the geofence and route-resolver hot paths — the same shape
  `routes.origin` already has against `origin_location_id` (076) — so no join is added to
  geofence evaluation.
- **Append-only, and never an UPDATE-by-id.** A shared row would let one entity's edit
  rewrite another's (two drivers on the same street), and an UPDATE keyed on a
  client-supplied `addressId` would let the client choose which row to overwrite —
  exactly the value this feature exists *not* to trust. A save writes a new row and
  repoints the FK; superseded rows are inert orphans.
- **Operational addresses must be verified to save; personal ones are advisory.**
  Locations and the hotel base refuse to save unverified; driver and emergency-contact
  addresses save as unverified, badged but never blocking.
- **Personal addresses geocode only on an explicit `[Verify address]`**, so typing costs
  no network request at all. Operational ones geocode as you type.

The two rules the whole feature hangs on:

1. **Selection is what verifies.** Typed text is never `verified`, however complete it
   looks. Only choosing a suggestion and having the *server* resolve it sets that.
2. **Editing invalidates the pair.** `src/lib/address/invalidate.js` clears latitude,
   longitude, components, verification and any *provider*-sourced ZIP in the same
   operation that changes the text, so there is no instant in which the form holds new
   text beside an old coordinate — "Address B with Latitude A" is structurally
   unsubmittable rather than merely discouraged. A **manually typed** ZIP deliberately
   survives the edit, flagged as needing confirmation, because it is the operator's own
   assertion rather than a property of the address being replaced.

**The provider is blocked, and it is not a code problem.** The server key returns `200`
on `/routing/1/calculateRoute` but `403 {"code":"Forbidden","message":"You are not allowed
to access this endpoint"}` on `/search/2/search`. The two TomTom keys in `.env` are
different, so this is not a mix-up: the Search API is simply not enabled for that key in
the TomTom portal.

The diagnostic that settled it is the reusable part. A 403 has several causes that need
*different* fixes — API not enabled, an origin-restricted key, a wrong key, a quota — and
the bare status code cannot distinguish them. So `scripts/check-address-provider.mjs`
probes **routing first, with the same key**, as a known-good baseline (it is the TomTom
call this app already makes successfully in production), then probes search, and prints
the error body. Routing-OK + search-403 narrows it to a missing permission in a single
run. The first version of that script printed only `HTTP 403` and told us nothing —
TomTom puts the reason in the body, and discarding it is what made the earlier run
useless.

**This also means the PH component mapping is still an assumption.** `parse.js` maps
TomTom's `municipalitySubdivision` to `barangay`, and no real payload has ever been
observed. The unit tests cannot settle it: they assert that a field the provider does
**not** send stays NULL, which is true under either mapping, so **76 passing tests prove
nothing about this**. Worth recording because it is the `200 []` lesson wearing different
clothes — a green suite is not evidence for a claim the suite does not test.

**The one gate still open, and the evidence says it is not this code.** `npm run build` dies
with `FATAL ERROR: NewSpace::EnsureCurrentCapacity Allocation failed — JavaScript heap out of

The detail that settles the diagnosis is the heap sizes in the GC lines: **14.7 MB → 12.3 MB
→ allocation failure**, and elsewhere 22.8 → 17.5 MB, 27.3 → 22.1 MB. A worker failing to
allocate a young generation of tens of megabytes is not a module leaking memory — it is the
machine having none to give. The same environment fault is already recorded against a
full-repo `vitest run` in this note, and two runs produced two different native exit codes
(`3221226505` / `0xC0000409`, then `134` / `SIGABRT`) from the same cause, which is what a
resource exhaustion looks like rather than a deterministic code defect.

The supporting argument is that the new components are `"use client"` and **no page imports
them yet**, so the only new entries in the build graph are the five `/api/geo/*` handlers —
and those are the same shape as the other 162 route files. That is reasoning, though, and
this note has already recorded once that reasoning about a build is not a build. **So: the
build has not been observed to succeed, and nothing here claims it has.** It stays red until
a green run exists.

**A third run reversed the fix direction, and this is the part worth keeping.** Having
concluded "system memory pressure", the obvious next move is to give Node more room, so the
run was repeated as `NODE_OPTIONS=--max-old-space-size=4096 npm run build`. It failed
**earlier** and **differently**:

```
▲ Next.js 16.2.11 (Turbopack)
  Creating an optimized production build ...
memory allocation of 2078912 bytes failed
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
```

Three things follow from that output, and they matter more than the fact that it failed.

- **It is not the V8 heap.** `memory allocation of N bytes failed` is the Rust global
  allocator giving up — Turbopack is Rust, not Webpack — and it was refused a **2 MB**
  allocation. A 4 GB V8 heap limit had just been granted, so the ceiling being hit is the
  operating system's commit charge, which neither `--max-old-space-size` nor any `next.config`
  key raises.
- **Raising the heap made it worse, not better.** The failure moved *backwards*, from
  "Collecting page data" (after compile and type check succeeded) to "Creating an optimized
  production build" (before them). A 4 GB reservation is a large thing to ask a machine that
  is already refusing 2 MB, and it competes directly with the native allocations. So the
  earlier note "the likely fix is … a larger `--max-old-space-size`" was **wrong**, and is
  corrected here rather than left standing.
- **The lever is concurrency, not allowance.** Fewer simultaneous workers asks for less at
  once; more heap asks for more. Everything known so far points the other way from the
  first guess.

Next's own guide at `node_modules/next/dist/docs/01-app/02-guides/memory-usage.md` was read
for a targeted knob and is **largely inapplicable here**: every lever it names —
`webpackMemoryOptimizations`, `webpackBuildWorker`, disabling the Webpack cache, the source
map options — is Webpack-specific, and this build is Turbopack. That is worth recording so
the next person does not spend the same time reading it. `next.config.mjs` was read too and
carries nothing relevant: `output: "standalone"` (which does add a tracing pass) and
`turbopack.root`, no memory or worker settings.

**The lever, read out of Next's own source rather than guessed.** The "11 workers" in the
failure message is not a constant — `node_modules/next/dist/build/index.js:309`
(`getNumberOfWorkers`) derives it, and `node_modules/next/dist/server/config-shared.js:202`
sets the default as:

```js
cpus: Math.max(1, (Number(process.env.CIRCLE_NODE_TOTAL) || (os.cpus() || {length: 1}).length) - 1)
```

So 11 workers means this machine reports **12 logical CPUs**, and Next's default is to fork
one worker per core less one. The page-data phase is exactly where the OOM landed, and 11
concurrent forked Node processes — each loading a server bundle — is a plausible way to
exhaust a commit charge that is already refusing 2 MB.

The source also hands over a zero-change way to test that: `CIRCLE_NODE_TOTAL` feeds the
default. Setting `CIRCLE_NODE_TOTAL=2` makes the default `cpus` 1, which is equal to the
value `getNumberOfWorkers` compares against, so the user-override branch is not taken and
the function returns **1 worker**:

```
CIRCLE_NODE_TOTAL=2 npm run build
```

That was the experiment to run, and **it ran, and it went green** — so the worker pool is
confirmed as the cause rather than merely suspected. (Do **not** reach for
`experimental.memoryBasedWorkersCount` — line 315 floors the result at a **minimum of 4**
workers, so it cannot go low enough to help a starved machine.) For the compile stage, which
is the one the 4 GB run died in, `node_modules/next/dist/build/turbopack-build/index.js:31`
runs Turbopack in a **worker thread** (`numWorkers: 1`) unless `NEXT_TURBOPACK_USE_WORKER=0`
is set, which runs it in the main process instead — a second, independent lever that this
build did not need.

**The design decisions worth keeping:**

- **Derive the geography, do not reconcile it.** The server discards the client's
  `regionName`/`provinceName`/`cityName`/`barangayName` and rebuilds them from the one
  thing it believes — the chosen `psgc_barangay_code`. Rejecting on a text mismatch was the
  first design: it catches nothing that ignoring does not already catch, and it permanently
  strands any address whose barangay was renamed by plebiscite after it was saved. This is a
  deliberate departure from what the plan said (`reject any mismatch`), and the reason is in
  the file header.
- **Province required *unless the city has none*.** Metro Manila has no provinces, so the
  rule is answered by the data — an empty province list from a region that loaded
  successfully — never by a hardcoded region list. `200 []` from a *failed* request must not
  be read as "no provinces", so the flag turns on `isSuccess`, not on "not loading".
- **The importer refuses to infer parentage from the digits.** PSGC codes are hierarchical
  in principle, so masking the last N digits is tempting — but the layout is not uniform
  (the province segment is meaningless for the NCR cities) and block widths have changed
  between revisions. A mask wrong for one class of code files addresses under the wrong
  parent, silently. Parents are stated in the file and validated against it.
- **The pin is a claim, not a verification.** `verified` is false and `provider = 'manual'`
  on every row this form writes, and the map says so in words. `address-map-preview.jsx`
  refuses click-to-place for exactly this reason; `address-pin-map.jsx` **is** a picker, and
  the resolution is to make the honesty explicit rather than to pretend the tension is gone.
- **Only regions are seeded (17).** Provinces, cities and barangays are not — inventing
  them from memory asserts barangays that may not exist, which is the "never invent" rule.
  The consequence is deliberate and visible: the form renders empty states below Region
  until someone runs the import.

**Two silent-correctness bugs I caught by re-reading my own code**, both of which would have
produced plausible wrong behaviour with no symptom:

1. `selectLevel` reset the levels below the change **after** applying the selection, and
   `clearBelow("city")` includes the `cityHasNoProvince` flag — so the flag was always
   clobbered back to `false` and **every Metro Manila address would have demanded a province
   that does not exist**. The exact failure the module is built to prevent. Reset first, then
   spread the selection. Two tests added, because the existing suite was blind to it.
2. `const listId = \`${id ?? useId()}-listbox\`` short-circuits, so `useId()` is skipped
   whenever a caller passes an `id` — a rules-of-hooks violation that desyncs hook order
   between renders and breaks the component *only for callers that supply an id*.

Neither was reachable by running anything, since nothing could run. They were reachable by
reading, which is the weaker instrument — and the honest framing is that a third one
probably survives.

**One thing I had to correct in myself.** The `ph_barangays` entry in
`scripts/lib/schema-contract.mjs` originally asserted that *"the 2026-09-23 probe returned a
refusal, not `200 []`"*. No probe had run and the migration is not applied. That is
**fabricated evidence inside the file whose entire purpose is to prevent it** — the `200 []`
lesson, inverted, written by me, one paragraph after I had quoted it. Rewritten as an
explicit "NOT YET VERIFIED against live".

**The read-only audit, which is the one check that *could* run.** Reading and searching do
not need the safety classifier, so the whole import surface was checked by hand: every
`import` in the seven new files resolves to a real export (`FloatingShell` and its props,
`Dialog`/`DialogContent`/`DialogFooter`, `Popover`/`PopoverContent`/`PopoverTrigger`,
`EmptyState` with `size`/`variant`/`title`/`description`, the five `geography.service`
functions against the five `/api/geo/*` routes and their query-parameter names), the
`editDetail` / `selectLevel` / `structuredErrors` signatures match every call site, and
`update_updated_at()` is the real shared trigger function with the repo's
`update_<table>_updated_at` naming.

That audit is the weaker instrument — it is exactly the check that would have caught the
`AppPrivacyVeil` named/default mismatch recorded above, and it caught something here:
**two comments claimed the server "compares" the submitted region/province/city text** —
in `src/app/api/geo/resolve/route.js` and in the migration header — when the design
deliberately discards it and derives instead. Both now say so. This is the same defect as
the `transaction-integrity.js:91-92` contradiction further up this note: a comment stating a
rule the code does not implement, which is worse than no comment, because it is the thing
the next reader trusts. It changes nothing at runtime and everything about what someone
believes about the write boundary.

### Closed the harness leak and cleared the 19 (code change)

Two defects the login-failure diagnosis surfaced, both turned from cosmetic into
blocking by mandatory email OTP.

**The leak.** Only two scripts actually leaked: `verify-p1-e2e.mjs` and
`verify-p2-analytics.mjs`, whose `finally` blocks were `pool.end()` and nothing
else. `verify-cancel-cascade.mjs`, `verify-trip-status.mjs` and
`verify-quickwins.mjs` already soft-deleted what they created. Both offenders now
track the ids they insert and soft-delete `fuelrecords → trips → vehicles →
drivers → employees` in the `finally`, before `pool.end()`, wrapped so a cleanup
failure logs rather than masking the test result.

`verify-p2-analytics.mjs` had a **second** defect that made it accumulate rather
than merely leak: its opening "CLEANUP PREVIOUS TEST DATA" block swept
`fuelrecords` and `trips` but not its own employee/driver rows, so every run
added another `analytics_driver_<epoch>@example.com` on top of the last. It now
sweeps prior fixture employees and drivers by address pattern too, so repeat runs
self-heal.

One trap worth remembering: that same script called `process.exit(1)` when a test
failed. `process.exit()` terminates immediately and **skips the `finally`** — so
the teardown would have leaked fixtures on exactly the runs that were already
going wrong. It sets `process.exitCode` instead. Every `process.exit(1)` in a
script with a `finally` is this bug.

**The backlog.** `scripts/cleanup-harness-fixtures.mjs`, new, modelled on
`soft-delete-otp-collision.mjs`. Dry-run by default; `--apply` to mutate;
`--expect <n>` required *with* `--apply`, so the operator must state up front how
many accounts they expect to sweep and a pattern that quietly starts matching real
accounts fails closed. Guards, any of which abort the whole run rather than
skipping a row: a matched row carrying an **operation role** (admin, super_admin,
fleet_manager, dispatcher, management) **or** a `password_hash`, and a candidate
vehicle carrying any trip or fuel row from a non-fixture driver. `driver` is
permitted — the premise that every fixture is role-less did not survive the
follow-up below.

Soft delete, not `DELETE` — `drivers.employee_id` has no `ON DELETE CASCADE`
(`schema.sql:1158`), nor do `notifications` or `audit_logs`, so a hard delete would
need an ordered unwinding across ~8 tables.

Four of the rows matched **no current script** (`testdriver1@example.com`,
`testdriver2@example.com`, `test-driver-<n>@example.com`), so the cleanup matches
observed address patterns rather than only what today's two scripts produce.

**The audit.** `audit-otp-inbox-ownership.mjs` now tracks whether any `OTP_FIX_*`
key loaded at all. With none, it labels the bucket `OWNED (unknown — env not
loaded)` and says ownership could not be assessed, instead of printing a `0` that
reads like a real regression. This is the `200 []` lesson from SEC-DB-003 in a
different script: an absence of evidence must not render as a finding.

### `verify-p1-e2e.mjs` had never once passed — and that is *why* it leaked (code change)

The teardown above stopped the leak but left the script failing on every run, and
those are one fact, not two: each failed run created its fixture, threw, and
abandoned it. Diagnosing the failure properly turned up **four independent defects
stacked behind the first error**, each one visible only once the one before it was
cleared.

1. **The fixtures had no role.** Employees were inserted as
   `(first_name, last_name, email)` — no `role_id`. `resolveCurrentIdentity`
   (`src/lib/api/utils.js:146`) rejects any identity whose `role_name` is null, so
   every bearer request 401'd at Scenario A. The fixtures now resolve the `driver`
   role and refuse loudly if it is absent.
2. **The tokens carried no `authVersion` or `familyId`.** `signAccessToken` alone
   is not enough: `resolveCurrentIdentity` re-reads `auth_version` (`:151-153`) and
   requires a live, unrevoked `mobile_refresh_tokens` row for the token's family
   (`:155`, `:165-175`). So fixing (1) only changed the 401's *message*, from
   `Unauthorized` to *"Session expired. Please sign in again."* — one problem
   wearing the clothes of another. The script now mints a real token family,
   mirroring `POST /api/mobile/auth/login` (`route.js:248-272`) minus the password
   and OTP steps a reserved-domain fixture can never pass, and deletes those rows
   in the teardown: they are credentials, not junk, and would otherwise outlive the
   account as valid 30-day sessions.
3. **The receipt URL had a doubled separator.** `.env` sets
   `NEXT_PUBLIC_SUPABASE_URL=https://<ref>.supabase.co/` *with* a trailing slash,
   and the script appended `/storage/v1/...`.
   `isOwnedFuelImageUrl` (`src/lib/fuel/receipt-storage.js:188`) matches the path as
   a **raw prefix**, so `//storage/...` failed ownership and the endpoint answered
   400 before reading any fuel data — presenting as a receipt problem rather than
   the auth one it had been.
4. **A rejected scenario stranded its fuel request.** `uq_fuelrequests_open_vehicle`
   (`migrations/066:55`) allows one request per vehicle with status
   `Pending`/`Approved`. A successful submission resolves its request to
   `Fulfilled` and leaves that predicate; a **rejected** one does not — and Scenario
   C is rejected by design (409, tank capacity), so its request stayed open on the
   vehicle and the later insert for that same vehicle collided with it. The harness
   now retires any open request before raising a new one, which is what an approver
   would have to do anyway. `Rejected` rather than `Fulfilled`: no fuel was
   delivered, and `fuelrequests_status_check` (`schema.sql:581`) permits only
   Pending/Approved/Rejected/Fulfilled — the first two sit inside the index
   predicate and would not clear it.

**A prediction I got wrong, and what it cost.** I expected Scenarios C, D and E to
be *refusals*, and therefore expected D to strand a request and break E. D and E
returned **201** — a wrong fuel type and a 150/L price are **flagged**
(`flags.fuel_type_mismatch`, `flags.price_anomaly`), not refused. Only C was a real
rejection, and it broke F3, one scenario later. The mechanism I had reasoned about
was right; the scenario I said it would break was wrong. Reading the code correctly
is not the same as knowing what it does at runtime.

**The cleanup guard was relaxed to match.** It aborted on any non-NULL `role_id`,
on the premise that every leaked fixture was role-less. Defect 1 retired that
premise, so it now permits `driver` and aborts on every other role. The lock that
actually matters is unchanged: matches are confined to `@example.com` by the address
patterns, a reserved domain `isDeliverableEmailAddress()` refuses, so no match can
be an account anyone could sign into.

**Then I made the script assert something (code change).** Every scenario only

precisely how all four defects survived unnoticed. There is now a
`check(label, condition, detail)` collector that **records** failures instead of
throwing on the first one, so a wrong response cannot hide the scenarios after
it; the run ends with a summary list and `process.exitCode = 1`. **Not
`process.exit()`** — that terminates immediately and would skip the `finally`
block, leaking fixtures on exactly the runs already going wrong. The `catch` also
sets the exit code now; previously a crash was swallowed and the script exited 0.

Two things I found while working out what the assertions should *say*, and both
changed what I wrote:

- **Scenario C is not a duplicate test, and its name says it is.** It never
  reaches `detectDuplicateReceipt`: the tank-capacity gate (`route.js:250`) runs
  first (`:262`), and the fixture submits 40 L into a 50 L tank at 30% full —
  about 35 L of space — so it is refused on capacity. Worse, reaching it would
  not have helped: Tier 2 is explicitly non-rejecting (`transaction-integrity.js:118-134`),
  it only sets a flag. So its expected `409` was never the duplicate rule, and my
  first instinct — that C was the cross-driver test — was wrong. The assertions
  now pin the refusal **and the reason**, and the run prints a warning, because
  accepting any `409` as a pass is exactly how this looked healthy while testing
  nothing. I did **not** change the fixture: making it reach Tier 2 would have
  been a second, separate change folded into "add assertions", and it would only
  have earned a red assertion anyway (next bullet).
- **`possible_duplicate` has never once reached a record — a product defect, not
  a harness bug.** `route.js:206` serialises `flags` into the query `values`
  *before* the transaction opens; `:275-277` then sets `flags.possible_duplicate`
  on the already-serialised object, and the `INSERT … RETURNING *` at `:279`
  writes the pre-mutation copy. Tier 2 is the only thing that sets that flag, so
  it has always been thrown away. Scenario F2 proves it live: it re-submits E's
  exact station / date / liters / amount, Tier 1 cannot fire because
  `receipt-12345` is new, so Tier 2 matches — and the flags come back
  `{price_anomaly: true}` only. Also found: `transaction-integrity.js:91-92`
  claims Tier 2 *"intentionally excludes the submitting driver's own records"*,
  but the query passes only `[stationName, fuelDate, liters, amount]` — **there
  is no driver predicate at all**, so a driver's own prior submission is what
  usually matches. I left both as red assertions rather than fixing them:
  moving the write changes what real records store, and the comment-vs-query
  contradiction has to be settled first. Folding that into a test-harness change
  is exactly the kind of silent behaviour change this whole effort is about.

**F3 turned out to be the real cross-driver test** — Tier 1 on the transaction id

check is not scoped to the submitting driver, and it was already there, just

not the whole contract: a refused submission must leave **no row** (a `409` is a
rollback, not a partial write), an idempotent replay must not store a second
copy, and the accepted set must be exactly the five expected records.

## Decisions made

- **No change to the login path.** The address move was intentional (mandatory
  email OTP requires a mailbox the employee actually owns) and the fail-closed
  behaviour is by design, so `admin@gmail.com` failing is data/ops, not a code
  defect. Recorded the corrected finding in `Bugs.md`. The changes made instead
  were to the two *harnesses* that leak accounts and to the audit that reports on
  them — neither touches authentication.
- **Soft delete over hard delete**, matching the precedent in
  `verify-cancel-cascade.mjs` / `verify-trip-status.mjs` / `verify-quickwins.mjs`.
  `drivers.employee_id` has no `ON DELETE CASCADE`, so a hard delete would need an
  ordered unwinding across ~8 tables to clear FK references that soft delete
  leaves perfectly valid.
- **The cleanup refuses rather than skips.** Any guard failure aborts the entire
  sweep. A partial sweep of a set that surprised us is the outcome the guards
  exist to prevent, so "skip the odd row and carry on" would defeat them.
- **`--expect <n>` is required with `--apply`**, not optional. It forces the
  operator to state the expected set size up front, so a pattern that starts
  matching real accounts — or a harness row created between the dry run and the
  apply — fails closed instead of being swept.
- **Harness fixture roles are resolved from the permission matrix, not hard-coded.**
  `verify-p2-analytics.mjs` asks `rolesFor("reports", "read")` which roles may reach the
  endpoint rather than naming `admin`, so the harness cannot drift from the matrix that
  gates the route. `super_admin` is excluded from the candidate list on purpose — it is
  an explicit bypass, so a fixture holding it would pass even if every real role had lost
  the grant. The same reasoning drove `verify-p1-e2e.mjs` to look its `driver` role up
  rather than assume an id.
- **Minted tokens are deleted, not soft-deleted.** They are credentials, not fixture
  rows: `mobile_refresh_tokens` has no `deleted_at`, and a surviving row is a valid
  30-day session against an account the teardown just retired.
- **Sign-out clears biometric.** The alternative — a surviving local credential that
  biometrics unlock into a fresh session — would have required a second token class, a
  biometric mint endpoint, or a trusted-device bypass, all of which the brief forbade
  and all of which would have made the phone a credential the server never issued. So
  Sign Out revokes the family *and* destroys the enrollment, and LOCK is a separate
  operation that touches neither.
- **The lock screen's "Sign in with password" is a real sign-out** (behind a confirm),
  not a bypass. A new session needs the password *and* the emailed code, and the server
  will not mint one while the old family is alive — pretending otherwise would be UI
  that lies.
- **No login-screen biometric button.** With sign-out clearing biometric, the app never
  lands on login while biometric is enabled — cold start goes to the lock screen. The
  button would have been unreachable, so it was dropped rather than shipped as decoration.
- **No `authentication_method = "biometric"` audit event.** The server cannot verify a
  device-local assertion, so the row would be a claim we could not stand behind.
- **5 minutes matches the existing web idle timeout** (`IDLE_TIMEOUT_SECONDS = 300`),
  so both channels agree on what "idle" means. One constant, not a user setting.
- **Two `AppState` listeners, deliberately not merged** — the existing one drives
  `syncQueue()`, and folding the lock into it would put offline sync at risk for no gain.
- **`expo-screen-capture` is a dependency, not a config plugin.** The plugin adds
  `DETECT_SCREEN_CAPTURE` for the screenshot-listener API, which is not used;
  `preventScreenCaptureAsync()` sets `FLAG_SECURE` at runtime.

### `mobile/.easignore` does not do what its comment says (found while building)

The build log carried a warning that reads like a footnote and is not one:

> File specified via `android.googleServicesFile` field in your app.json is not checked in
> to your repository and won't be uploaded to the builder.

`mobile/.gitignore:41` ignores `/services/google-services.json` (Firebase config contains
API keys, so it stays out of git — correct). `mobile/.easignore` then deliberately does
**not** list it, and closes with:

> `/services/google-services.json` is intentionally NOT ignored here — EAS needs it in the
> build archive. It remains gitignored.

That reasoning is wrong, and the build log is the evidence. **Not being ignored by
`.easignore` is not sufficient** — EAS separately requires the file to be git-tracked, or
supplied as a *file environment variable*. This applies the `200 []` lesson again: a
config comment stating an outcome is not the same as the outcome, and only running the
thing showed the difference on the secondary check.

Consequence for this artifact: it built successfully, which means the `google-services`
Gradle plugin was not applied rather than failing — so **FCM is not wired into this dev
client and push notifications will be inert on it**. That does not affect the biometric
E2E above, which exercises no push path, but it does mean a silent push failure on this
binary is expected and is not a biometrics defect. The fix is to hand the file to EAS as a
secret/sensitive file environment variable, which keeps it out of git as intended.
