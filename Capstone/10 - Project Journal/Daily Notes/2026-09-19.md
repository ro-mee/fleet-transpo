# 2026-09-19

## What I worked on

One thread: the paired `[coach-marks] Two live targets share the id` warnings that the device had started printing on the Incident screen. Asked to analyse them, then to implement three of the four fixes the analysis produced.

### The warning, and what it actually said

```
WARN [coach-marks] Two live targets share the id "incident.category" with different bounds
(16,328 379.4285583496094x301.7142333984375 vs 16,182.28570556640625 379.4285583496094x302.2857360839844).
The spotlight follows whichever measured last — give the target id to one instance only.
```

Six of these in a row, alternating which pair was labelled "this one" and which "previous", and the last pair differed in `y` by exactly 47.43 dp.

My first read of the numbers was wrong and worth recording: I took `16,328` as `x=16, y=328` against `x=182.29`, which would have made the two boxes *different elements* side by side. They are not. `x` is 16 for both — and 379.4286 is the screen width minus the 32 dp that `styles.scroll`'s `paddingHorizontal: 16` takes — so both boxes are **the same element at the same width on the same route**, offset vertically. That single observation did most of the work: it ruled out "two different controls colliding" and left "two live mounts of one target".

`byToken.size > 1` in the warning is only reachable with two **live** registrations, so two instances of `incident.category` were mounted. The alternation proved both were still re-measuring — a single frozen ghost would have logged once, not six times with the labels swapping. And 145.71 dp of vertical offset matches the conditional Vehicle section above the grid (`{!tripId && vehiclePlate && …}` at `incidents.js:306-319`) rendering in one instance and not the other.

### What could produce a second live mount

`mobile/app/(app)/_layout.js` has exactly one `CoachMarkProvider` and one `Stack`; `incidents.js` has exactly one `incident.category` target. So the second mount is not a second provider. It is a mount that **stays alive off-screen**, and there are three of those:

1. A covered stack screen — `NativeStackView` keeps previous screens mounted.
2. A background tab — the `(tabs)` screens stay mounted after first visit (the reason `mobile/lib/tracking.js:3` uses `useIsFocused` for its watcher).
3. A route mounted ahead of time by `router.prefetch` — `(tabs)/index.js:394-403` prefetches `QUICK_ACTION_ROUTES`. A PRELOAD navigation action pushes into `state.preloadedRoutes`, and `NativeStackView` renders those as an inactive `Screen`.

(3) is the one I could not fully settle: those screens render with `display: 'none'`, which predicts a **zero-size** measurement, and `registerTarget` rejects `width <= 0` — so if prefetch were the only producer, there should be no warning at all. But the guard only rejects at registration; `styles.scroll`'s width and a stale-but-positive layout are both conceivable, and I did not have a device to settle it. Rather than pick a winner, the fix is a filter on all three producers at once.

### The three fixes

1. **Focus-scoped registration.** `CoachMarkTarget` now reads `useIsFocused()`. A blurred instance does not measure, and losing focus **drops** its registration — a blurred instance's bounds describe a screen the driver has left. Regaining focus re-registers on its own, because `isFocused` sits in `measureAndRegister`'s deps and its identity change re-runs the measurement effects. This is what makes the whole producer list moot: covered screen, background tab and preload are all simply not focused.
2. **Closed the ghost-registration window.** `measureInWindow` is a native round trip and the 320 ms scroll-settle timer is a timer; both outlive the render that scheduled them, and a registration landing after unmount is never cleaned up — the provider keeps the entry forever and it stays eligible to win the spotlight. `canRegister()` (mounted **and** focused, mirrored into refs by `useLayoutEffect`) now guards every async measure callback, and the settle timer is `clearTimeout`-ed on unmount so it cannot fire after the unregister that would have removed it.
3. **The dev warning now names the culprit.** It reports both instances (a dev-only module counter — the ownership token is a `Symbol`, which logs as `Symbol(coach-mark-target)` and identifies nothing), their routes, the live-instance count under the id, and the registering stack. The stack is the part that matters: the bounds alone cannot distinguish a mount effect from a settle timer from a measure callback that had outlived its screen.

Fix 4 from the analysis — reconsidering the warning copy for `inspection.remarks`, which is *legitimately* live more than once — was deliberately not implemented.

Five tests in a new `describe("One instance, one spotlight")` block in `mobile/lib/coach-marks.test.js`, bringing the file from 39 to 44.

## What I learned

**Fixing the producer you can name is not the same as fixing the class.** I could not prove which of the three off-screen mounts was behind the second registration, and I spent real effort trying. The focus gate dissolves the question instead of answering it: whatever mounts the duplicate, it is not focused, so it cannot publish. When a bug has several candidate causes that are all instances of one property, gate on the property.

**Two rectangles with the same `x` and width are one rectangle.** The geometric read — same x, same width, differing only in `y` — collapsed the search space before any code was read. I nearly skipped it: my first parse of `(16,328 …)` as `x=16, y=328` was wrong in a way that would have sent me looking for two different controls. Reading the numbers as they were actually formatted, rather than as I expected them, was the whole of the analysis. And the third data point is what confirmed it: `328 vs 280.57` is 47.43 dp, not 145.71 — so the offset *changes* between measurements, which is what a section that renders conditionally in one mount and not the other looks like, and not what a fixed layout difference looks like.

**A warning that says "give the target id to one instance only" was telling the truth and still useless.** That advice cannot be followed for a mount you cannot see. The warning's job was to name the instance, and the identity it had available — a `Symbol` token — is deliberately unprintable, so it printed nothing. Instrumentation has to be designed for the question it will be asked, not for the state it happens to hold.

**`useIsFocused` is the right primitive here, and the repo already said so.** `mobile/lib/tracking.js:3` uses it for exactly this reason, with the reason written down: the tab screens stay mounted after being visited. The precedent was three lines into a file I had already read earlier in the session, and I found the duplicate-mount mechanism from first principles before finding the existing answer to it.

**The settle timer was the one bug in this batch I could not have found by reasoning about focus.** The mount guard and the focus gate are both about *whether* to register; the timer is about *when*, and a 320 ms timer outliving an unmount by a fixed amount is invisible until something unmounts slowly. It is also the only registration path that nothing else would have cleaned up: an entry written after the unmount-time unregister has no owner left to remove it.

## Decisions made

- **Gate on focus, at every registration, not at the point where the work is scheduled.** The scheduling point is a render; the work outlives it. `canRegister()` re-reads refs written by `useLayoutEffect`, which lands at commit — before a pending continuation can read a stale value. This is the same reasoning (and the same mechanism) as `isDrivingRef` / `overlayVisibleRef` in the provider.
- **Losing focus unregisters, rather than merely suppressing new registrations.** Suppression alone leaves the last focused measurement live, so a blurred duplicate still owns the spotlight until it happens to re-measure. Unregistering makes "blurred" and "not registered" the same state.
- **Mirror `isFocused` into a ref as well as using it directly.** The direct read is the gate at scheduling time; the ref is for the async callbacks. Both are needed and they answer different questions.
- **`instanceId` behind `__DEV__`.** A module-level counter is the simplest thing that distinguishes two mounts of one id in a log line, and it costs nothing in a release build.
- **Fix 4 not implemented**, as scoped. The `inspection.remarks` warning copy stays as it is.
- No `try`/`catch` around `useIsFocused()` even though this file wraps `usePathname()` in one — `mobile/lib/tracking.js` calls it bare, and matching the existing usage is worth more than defending a call that only throws outside a navigator.
