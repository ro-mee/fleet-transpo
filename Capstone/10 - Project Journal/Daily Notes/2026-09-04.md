# 2026-09-04

## What I worked on

### Live-map error banners — diagnosed, no code defect

User reported both `QueryErrorBanner`s on `/tracking/live-map` ("Unable to load
active trips" + "Unable to refresh GPS positions") and hypothesized they appear
because there are no active trips.

Findings, each verified against live:

- **Not an empty state.** The banners render only on `query.isError`
  (`QueryErrorBanner` returns null otherwise); empty success renders the
  `EmptyState` instead. Both endpoints return `ok(rows)` (HTTP 200) even with
  zero rows.
- **DB is healthy and the data exists.** One trip matches
  `LIVE_TRIP_STATUSES` (trip_id 451, "At Pickup"); 359 gpstracking rows. The
  exact SQL of both `/api/trips/active` and `/api/trips/latest-locations`
  (including the LATERAL latest-fix join) was run against the live DB — both
  succeed, 1 row each.
- **Both endpoints work end-to-end authenticated.** Minted a real NextAuth
  session JWT (employee 42, fleet_manager) + matching `web_sessions` row,
  called both routes with the cookie: **HTTP 200 with the live trip** on both.
  Diagnostic session row deleted afterwards. Server, auth chain, pool, and
  queries are all healthy.
- Unauthenticated requests get a clean 401 `{"error":"Unauthorized","code":"SESSION_INVALID"}`.

Conclusion: the banners the user saw were a transient/ session-level failure
(expired or invalidated web session — `auth_version` bumps on employees 48/49
invalidate older tokens), not a code bug. When a session truly expires, the
fetch interceptor in `session-manager.jsx` dispatches `AUTH_FAILURE` and the
expiry modal takes over, so the map banners are the fallback surface for
transient errors (network blip, dev-server restart) — retry recovers.

Fix for the user: reload the page / re-login if the expiry modal appears.
Nothing to change in code.

## What I learned

- Verifying "the endpoint works" requires the *authenticated* path — curl
  without a cookie only proves the auth layer responds, and earlier misread
  a 401 as a 404.
- A NextAuth session can be minted offline via `next-auth/jwt` `encode()` with
  `NEXTAUTH_SECRET` + a matching `web_sessions` row, which is enough to
  exercise any web API route as a logged-in user for diagnostics.
